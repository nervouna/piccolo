# Piccolo

Piccolo is a macOS menu bar app that moves, resizes and arranges windows with global keyboard shortcuts. MIT licensed.

The repository is public. Write every commit, issue and PR in English, with no secrets and no personal paths.

## Product scope

1. Menu bar app, no Dock icon, launches at login.
2. Every action can be bound to a global shortcut recorded in Settings: a key together with at least one of command, option or control, or a function key on its own. Shift alone does not make a shortcut, so a hand-edited config can never take over a plain key.
3. Place the focused window at a target frame: built-in presets (halves, thirds, quarters, center, maximize, ...) and user-defined rectangles expressed as fractions of the screen's visible frame. Pressing Left, Right, Top or Bottom Half again cycles the window through 1/2, 2/3 and 1/3 of the display. A Restore Window action puts a window back where it was before Piccolo moved it (one level, in memory, for windows Piccolo moved only).
4. Move the focused window to the next or previous display, or to the display to its left, right, above or below, keeping its relative frame.
5. Arrange the N most recently focused windows in a grid. Each shortcut is bound to one fixed combination (e.g. "last 4 in 2×2"). Candidates are windows on the current display and current Space; minimized and full-screen windows are excluded.
6. Linked resize: after Piccolo arranged windows side by side, stacked or in a grid, a shortcut moves a divider by a fixed step and the neighbouring windows follow, leaving no gaps or overlaps. Only groups created by Piccolo are linked. Groups are validated lazily: when a linked-resize shortcut fires and any member is no longer at its expected frame, the group is dissolved.

Non-goals: drag-to-snap with the mouse, automatic tiling of new windows, moving windows across Spaces, overriding system-reserved shortcuts, modifier-only shortcuts, Mac App Store distribution.

## Architecture

- Swift 6, SwiftUI + AppKit. Minimum macOS 14; raise it only when a dependency requires it. Not sandboxed (the Accessibility API rules it out), hardened runtime on.
- Bundle ID `io.damao.piccolo`.
- The root `Package.swift` holds everything testable:
  - `PiccoloCore`: pure logic (geometry, presets, grid and divider model, config schema). No AppKit side effects, no globals, fully unit tested.
  - `PiccoloSystem`: adapters for Accessibility, window enumeration, screens, hotkeys and the login item (`LoginItem`, over `SMAppService.mainApp`; its status and error types are in `PiccoloCore`), behind protocols so that logic is testable with fakes. The window catalog joins CGWindowList (order, window numbers) with Accessibility (kind, state, the handle that sets a frame) through `_AXUIElementGetWindow`, a private but long-stable API declared in one place (`WindowNumber.swift`); it rules out the Mac App Store, already a non-goal. The focus tracker keeps a `FocusHistory` from workspace and `AXObserver` events; the app starts it at launch (`AppDelegate`), so that the first arrangement already has a history, and the first use of `ActionExecutor.live` starts it as well if that comes first.
  - `PiccoloControl`: request/response protocol, server and client of the debug control channel. Imports nothing from the other targets, so test support apps can host a server too.
  - `PiccoloUI`: the Settings window. `SettingsModel` (`@MainActor`, `@Observable`; every edit is validated, then persisted through a `SettingsBackend` before it shows), the pure texts (`ActionSummary`, `ShortcutText`, `ActionPreview`), the SwiftUI views and `SettingsWindowController`. The login item switch ("Launch at login", General tab) goes through a `LoginItemBackend` the same way: the model reads the status when the tab appears, when the window opens or the app is activated and after every change, and shows a refused change under the switch. Depends on `PiccoloCore` only; the app plugs in the backends, so the model is unit tested against ones in memory.
  - `piccoloctl` (executable): command line client of the control channel plus read-only desktop queries (see "Debug control channel").
  - `PiccoloAcceptanceTests`: desktop acceptance tests, skipped unless `PICCOLO_ACCEPTANCE=1` (see "Desktop acceptance").
- `Piccolo.xcodeproj` holds thin targets only: the `Piccolo` app (UI and wiring, sources in `App/`) and the test support app `PiccoloFixture` (sources in `Fixture/`, see "Desktop acceptance"). It uses file-system-synchronized groups, so adding files does not touch the project file; a new target does, and the file is edited by hand. No project generators. A new package product the app uses (`PiccoloCore`, `PiccoloSystem`, `PiccoloUI`) is linked the same way each time: a `PBXBuildFile` in the app's Frameworks phase, an entry in its `packageProductDependencies` and an `XCSwiftPackageProductDependency`.
- Config and shortcuts: the config is `~/Library/Application Support/Piccolo/config.json`. Besides the bindings it holds `resizeStep` (default `0.05`), `animation` (`off`, `fast`, `medium`, `slow`; default `fast`), `gridFillOrder` (`rows`, `columns`; default `rows`) and `destinationPreview` (a boolean; default `true`). Every save writes all of them. A missing key takes its default without an issue; a key that cannot be read (an unknown name, a wrong JSON type) takes its default with an issue naming it, and counts as a dropped entry, as an invalid `resizeStep` does. `ActionSettings` (`PiccoloCore`) is what an action reads from the config: the resize step, the animation and the fill order. The hotkey path passes `ActionSettings(config)` of the config in effect when the key is pressed. A missing file means no bindings, with one exception: at launch, `ShortcutManager.loadAtLaunch(from:)` writes `Config.defaultShortcuts` (the 28 bindings of `PiccoloCore/Config/DefaultShortcuts.swift`) to a missing file through `ConfigStore.createIfMissing`, which never writes over an existing file, and then loads it. `config.load`, "Reload Config" and every other load of a missing file load no bindings and write nothing; the first save from Settings creates the folder too. Settings' "Restore Default Shortcuts…" goes through `ShortcutManager.replaceKeepingCopy(with:)`, which takes the bindings: it copies the file (`ConfigStore.backUp()`) and saves `Config.defaultShortcuts.bindings` in its place, keeping the settings in use. At launch, and on "Reload Config" in the menu, `ShortcutManager` (`PiccoloSystem`) loads it, resolves it with `ShortcutPlan` and registers the shortcuts as Carbon hotkeys through `HotkeyRegistrar` (the Carbon calls sit behind `HotkeyBackend`, so the replace and failure logic is unit tested with a fake). `ShortcutManager.save(_:)` writes an edited config to the file it has loaded (the default location, or the file given to `config.load`) and loads it again; `setSuspended(_:)` releases every hotkey and keeps loads and saves from registering any until it is lifted (see "Settings"). A hotkey runs its action through `ActionExecutor` on a serial queue, never on the main thread; failures are logged. The action runs when the shortcut is pressed, or, with `destinationPreview` on, when it is released (see the next item). Load issues, plan issues and shortcuts the system refused are logged and listed in `config.status`. When the last load dropped something (a skipped binding or a setting replaced by its default), the first save after it copies the file to `config.backup-<yyyyMMdd-HHmmss>.json` next to it before writing, once per load, and the issue list says where the copy is until the next load.
- Held shortcuts and the destination preview: with `destinationPreview` on (the default) a shortcut runs when it is released, not when it is pressed; with it off it runs on the press, as it always did. The hold rules are `HoldRules` (`PiccoloCore/Shortcuts`), a pure state machine from events (press, release, Escape, timer fired, cancel-all) to effects (run, show preview, hide preview, start timer), run by `HoldController` against an injected `HoldTimer`; each `ShortcutManager` owns one. A press starts a hold and a 0.2 s timer. Released before the timer fires (a tap), the action runs on release and nothing is shown. Still held when it fires, the preview is shown, and the release hides it and then runs the action. Escape while held hides the preview, and the release then does nothing. A press of any shortcut while one is held cancels the held one without running it and takes over, and that includes a press of the held shortcut itself: the system delivers no auto-repeat for a hotkey (measured, see below), so a second press of the shortcut that is held can only mean that its release was lost, and ignoring it would leave the shortcut dead with the preview and the temporary Escape (plain Escape for a bare function key) taken until something else ended the hold. A release of a shortcut that is not the held one is ignored. Cancel-all hides the preview and drops the held shortcut without running it: every load, save and suspend of `ShortcutManager` does it, so a config load, the preview being switched off and the recording of a shortcut in Settings all end a hold. So does the system going away, because the key-up may never arrive then: `ShortcutManager.cancelHold()` is called by a `HoldInterruptionSource` (`SystemHoldInterruptions`, `PiccoloSystem/Hotkeys`) on `NSWorkspace.willSleepNotification`, `screensDidSleepNotification`, `sessionDidResignActiveNotification` and `willPowerOffNotification`, and on the distributed notifications `com.apple.screenIsLocked` and `com.apple.sessionagent.screenIsLocked` (the names `loginwindow` contains on macOS 27; there is no workspace notification for a lock), so no temporary Escape survives a lock. The source takes its two notification centers as parameters and the manager takes the source, so the unit tests post the real names into plain centers and fire a fake source. Escape: while a shortcut is held `ShortcutManager` registers Escape (key code 53) with the held shortcut's modifiers as a temporary hotkey (`HotkeyRegistrar.registerTemporary`), so that its press cancels and is not delivered to the frontmost application. It stays registered until the shortcut is released or the hold is cancelled in another way, also after Escape itself (the shortcut is still down, and Escape's key-up must not leak to another app), and it is not registered when the held shortcut is on Escape itself, nor when the system refuses it (the hold works, only Escape cannot cancel it). `HotkeyBackend` has `onRelease` next to `onPress`. Measured on macOS 27 and documented on `CarbonHotkeyBackend`: a key that stays down delivers one press (key-downs flagged as auto-repeat, and a second key-down without a key-up, are not delivered; the keyboard's own repeat cannot be produced from a test, so this rests on the repeat flag; the hold rules depend on it, and a keyboard whose repeat did reach the app would restart the hold on every repeat), and the release is delivered also when the modifiers go up before the key (a flags-changed event with no flags, then the key-up without modifiers). When the rules say show, `DestinationPreview` (`PiccoloSystem/Preview`) plans on the action queue with `ActionExecutor.destinations(for:onlyPid:settings:)` and shows the result through a `HighlightPresenter`. The planning is read-only and shares its code with the run (`planSingleWindow`, `planArrangement`, `planDividerMove`): it answers the frames the action would apply (and, for an arrangement and a divider move, the window of each, in cell order) without changing a window or a group; a group that no longer holds is not dissolved by it, the real run does that on release. A planning error, or nothing to do, shows no highlight, and the release runs the action as it would without a preview. A plan that comes back after the release, or after another show, is dropped, so a release before the planning finished shows nothing. The highlight is `HighlightPanels` (`PiccoloSystem/Preview`): one borderless `NSPanel` per destination frame, at exactly that frame (canonical coordinates converted at this boundary), drawn by `HighlightView` as a rounded rectangle (radius 10 pt) in the system accent colour: fill at 20% opacity and a 3 pt border, resolved when drawn so that light and dark mode and the accent colour follow; it fades in and out in about 0.1 s. Window level `.statusBar` (25: above ordinary windows and floating panels, below menus; so in `CGWindowList` it is not among the layer 0 windows, and a test finds it by pid and frame), collection behaviour `canJoinAllSpaces`, `fullScreenAuxiliary`, `stationary` and `ignoresCycle` (on the current Space, also over full-screen apps, not in Mission Control or the window cycle). It must never take the focus or activate Piccolo (an app that has been the active application stops firing `hotkey.simulate`, see "Desktop acceptance"): a non-activating panel that cannot become key or main, ignores the mouse, does not hide when the app is not active (a panel does by default, and Piccolo never is), and is ordered front with `orderFrontRegardless()`, never `makeKeyAndOrderFront`. Enumerations of windows leave the panels out twice over: they list layer 0 windows only, and never a window of Piccolo's own process.
- Failure notice: when a shortcut fires and nothing can happen, the user sees why in a short notice in the middle of the display, for about 1 s. `FailureNotice` (`PiccoloCore/Notice`) is the enum of the reasons, its raw value the stable name used on the control channel: `accessibilityNotGranted`, `noWindow`, `ownWindow`, `windowNotChangeable`, `noOtherDisplay`, `nothingToArrange`, `gridDoesNotFit`, `noGroup`, `dissolved`, `cannotMove`. The mapping is in `PiccoloSystem/FailureNotice+System.swift` (it needs `WindowError` and the outcomes): `FailureNotice(error:)` for a thrown error (`WindowError`, `ArrangePlannerError`; no notice for `ActionExecutionError` and `ActionPlanningError`, which are config errors reported in Settings) and `FailureNotice(outcome:for:)` for an `ActionOutcome` (`moveToDisplay` with nothing to do is `noOtherDisplay`, `arrangeGrid` with nothing to do is `nothingToArrange`, a window that failed inside an arrangement or divider move is `windowNotChangeable`, the divider move reasons map one to one; no notice for `placeWindow` with nothing to do or for a success). The texts and symbols are `FailureNoticeText` (`PiccoloUI/Text`, in the `PiccoloUI` catalog like every text of the window) and the panel is `NoticePanel` (`PiccoloUI/Window`): an `NSVisualEffectView` (`.hudWindow`, radius 12 pt) with an SF Symbol and the text in the system font at 15 pt, centred on the visible frame of the display, shown for 1 s and faded out in 0.2 s; a new notice replaces the one showing and restarts the timer. It follows the panel rules of the highlight (see the destination preview): non-activating, never key or main, ignores the mouse, does not hide when the app is inactive, `orderFrontRegardless()`, level `.statusBar` (layer 25, so not among the layer 0 windows and left out of every enumeration of windows), `canJoinAllSpaces`, `fullScreenAuxiliary`, `stationary`, `ignoresCycle`; it must never activate Piccolo or take the focus. `ConfigController.run` (the hotkey path, on the action queue) maps the error or outcome and, when there is a notice, reads the focused window's frame there and shows it on the main thread through `NoticeController` (`App/`), on the display that holds the window, or the one with the mouse when there is none. `action.run` on the control channel and the planning of the destination preview never show a notice; only the run does.
- Cycling, Restore Window and the window records. The rules are pure and in `PiccoloCore`: `PresetCycle` (`Actions/PresetCycle.swift`) holds the three steps of the four halves (size along the axis 1/2, 2/3, 1/3 anchored to the preset's edge) and picks the next step from the window's frame, the display's visible frame and the window's record: a window is "at step k" when its frame is within 2 pt (`FrameTolerance`) of the frame of step k, or of the achieved frame recorded for step k of the same preset (a window that refused the exact size still cycles); otherwise the step is 0. `ActionPlanner.plan(_:windowFrame:displays:record:)` uses it for `placeWindow` with a half, and plans `restoreWindow` (`Action.restoreWindow`, written `{"type": "restoreWindow"}`): with a record whose `lastAchieved` the window is still at (2 pt) the target is the record's `origin` on the display that holds most of it, shifted inside the visible frame like any target; when the origin lies on no display it is the same size centred on the window's current display; otherwise `.nothingToDo`. Planning is shared by `run` and `destinations`, so the destination preview shows the next step and the restore target. The records are `WindowRecord` (`origin`, `lastAchieved`, `cycle: CycleStep?` with the preset and step) and `WindowRecords` (`PiccoloCore/History/WindowRecords.swift`, the update rules), kept in memory by `WindowRecordStore` (`PiccoloSystem`, shared by the copies of an `ActionExecutor` like `LayoutGroupStore`) and keyed by `WindowID`; a window without a number (`WindowFrameAccess.windowID` is `nil`) is neither recorded nor restorable and cycles by its frame alone. A run updates the store after it changed a window: a single-window action (`ActionExecutor.run`), every window of an arrangement that was placed (`arrange`) and every window of a divider move whose cell changed and that was not marked failed (`moveDivider`): when the window has no record or is not at its `lastAchieved` (the user moved it since), the frame before the action becomes the new `origin`; `lastAchieved` and the preset step (or none) are then set to what the action achieved. A failed window is not recorded. A restore that ran clears the window's record, and a restore that found nothing to do drops the stale record (a run does; planning never writes). The failure notice `nothingToRestore` is what the hotkey path shows for `restoreWindow` with nothing to do; a cycling press is never a notice.
- Settings: the window is an `NSWindow` hosting `SettingsView` (`SettingsWindowController` in `PiccoloUI`, owned by `SettingsController` in `App/`), not a SwiftUI `Settings` scene: a scene cannot be opened reliably from code in a menu bar app, and the window has to be shown, closed and made key from the menu, from a second launch and from the control channel. "Settings…" (⌘,) in the menu opens it. Launching Piccolo again while it runs (`open /Applications/Piccolo.app`, Finder) calls `applicationShouldHandleReopen` and opens it too. Every way of opening it ends in `SettingsWindowController.show()`, which orders the window front at once and, when Piccolo is not the active application, asks the system to activate it with `NSRunningApplication.current.activate(options:)` and the option `activateIgnoringOtherApps`. That option is deprecated since macOS 14 ("will have no effect"), so it is passed as its raw value `1 << 1` to keep the build free of the warning, and it is what makes the request work: measured on macOS 27 with a fixture window in front and `settings.open`, which has no user event behind it (the menu is drawn by another process there, so a click on "Settings…" is not an event in Piccolo either), the plain `NSApp.activate()` brought Piccolo forward in 6 of 10 rounds and `activate(options: .activateAllWindows)` in 5 of 10, and a request that is refused is never granted later (the window stays behind the other application); with `activateIgnoringOtherApps` added it was 10 of 10 in each of 4 runs. The system acts about 0.1 s after the request, so the window is on screen before Piccolo is active. `show()` only orders the window front when Piccolo is active already, and nothing in it asks LaunchServices to open Piccolo, so the reopen event of a second launch cannot start a loop of reopen events. Should a later macOS stop honouring the option, the acceptance test "Settings in front" (10 rounds) fails; the fallback to try then is `NSWorkspace.shared.openApplication(at: Bundle.main.bundleURL, configuration:)` with `activates = true`, which ends in `applicationShouldHandleReopen` and so needs a guard against asking twice. The model is the one place that edits: the window and the `settings.*` control commands call the same methods. Recording a shortcut suspends every global hotkey (`SettingsBackend.setShortcutsSuspended`, so an existing shortcut can be pressed to record it again), and every exit restores them: a key, Escape, the removal of the binding, a reload that loses it, the window closing or losing key status, the app being deactivated, `settings.cancelRecording`. While recording, a local event monitor takes the key press before the menu's key equivalents see it.
- Localization: the interface is shown in English (the source language) or Simplified Chinese, and ships eight languages: `en`, `zh-Hans`, `zh-Hant`, `ja`, `fr`, `es`, `pt-BR`, `de` (`AppLanguage` in `PiccoloUI`). The texts are two String Catalogs, written by hand (`extractionState: manual`): `Sources/PiccoloUI/Resources/Localizable.xcstrings` for `PiccoloUI` (views, `ActionSummary`, `ActionKind`, `ShortcutText`, `SettingsMessages`, the restore alert, the window title) and `App/Localizable.xcstrings` for `App/` (the menu, the message for a config file of a newer format; the app's synchronized group picks the file up). `Package.swift` has `defaultLocalization: "en"` and lists the `PiccoloUI` catalog as a processed resource; `Piccolo.xcodeproj` lists the eight languages in `knownRegions`. Every key lists all eight languages, each `translated`: the catalog test requires a non-empty translated value in every language, with the arguments of the English text. Every language has its `.lproj` (the built app has eight, in the app and in `Piccolo_PiccoloUI.bundle`, so that the system offers the app in all of them). The terms are macOS's own translations of the same things, read from the system's localization tables and not from memory: `docs/localization-glossary.md` lists each term with the table it comes from, and a new string that needs a term adds its row there first (zh-Hans: 设置, 快捷键, 辅助功能, 登录时打开). Because `PiccoloUI` has resources, Xcode builds a bundle target for it that is signed automatically; `scripts/build.sh` passes `CODE_SIGN_STYLE=Manual` so that the signing identity applies to it too.
  - Rules for `PiccoloUI`: nothing is looked up in the main bundle, which in the app is the app's own. Texts are `String(localized: "…", bundle: .module)`; the functions that produce texts take a `bundle` parameter (default `AppLanguage.currentTextBundle`, the module bundle), so that tests can read any language through `AppLanguage.textBundle` (the language's `.lproj` folder, whatever language the test process runs in). Views use `Text(localized: "…")` (`Views/LocalizedText.swift`: the same lookup, shown verbatim) or `String(localized:bundle:)` where a control wants a `String`. A SwiftUI control or modifier given a literal (`Text("…")`, `Button("…")`, `.help("…")`) would look it up in the app's bundle and is not allowed. `App/` does the same with `String(localized:)` and its own catalog. `CatalogTests` enforces it: it fails on such a literal, on a text the sources look up that no catalog key matches, on a catalog key no source uses, on a language missing from a key, on an empty value, on `en` or `zh-Hans` not being `translated`, and on a translation whose arguments differ from the English ones.
  - Texts with values use format arguments, not concatenation (`"Arrange \(count) in \(rows) × \(columns)"`), numbered in the catalog (`%1$lld`) wherever there are several, so that a translation can reorder them. In a key with arguments a literal `%` is written `%%`; in one without, `%`. Plural forms are catalog variations (the menu's "N shortcuts active") and use the plural rules of the language the app runs in, not of the Mac's region. Not localized: text produced in `PiccoloCore` and `PiccoloSystem` (config issues and plan issues, system refusals, `ShortcutManager.Status.summary`, log lines), the control channel (commands, errors), the README, the app name "Piccolo", key symbols (⌃⌥⇧⌘, the arrows) and function key names. The menu builds its own line for the shortcut count (`MenuContent.summary(of:)`), because `Status.summary` is PiccoloSystem's English text. The spelled-out key names of `ShortcutText` (Space, Help, Clear, Enter, Keypad 5, Key 12) are in the catalog; Simplified Chinese translates Space and Key 12 and leaves the others as they are.
- Language setting: Settings → General has a Language picker at the top: System default and the eight languages, each written in its own language (`AppLanguage.nativeName`). `SettingsModel.language` is the choice and `setLanguage(_:)` stores it through a `LanguageBackend` (the app's is `SystemLanguageBackend`; tests use `FakeLanguage`). It is stored as `AppleLanguages` in Piccolo's own defaults domain, `io.damao.piccolo` (`LanguageDefaults`): one code, or no key at all for System default. That is the key macOS reads for an app's language at launch, and the one System Settings → Language & Region → Applications writes, so the two agree; the config file does not hold the language. A change applies at the next launch: `SettingsModel.effectiveLanguage` is the language the running app was started in (`Bundle.main.preferredLocalizations`, read once at launch) and `restartRequired` says whether the choice differs from it, System default counting as the language the system's own list gives (`LanguageBackend.systemLanguage`, read from the global domain: System default on a Mac set to the language the app runs in needs no restart). When a restart is needed, the tab says so under the picker and offers Restart Now (`SettingsModel.restartNow()`). The model reads the stored choice again when the window opens, the tab appears and the app is activated.
  - Restart Now quits Piccolo and starts it again from a helper that does not depend on Piccolo staying alive: `AppRestart` starts `/bin/sh` with a short script (the process ID, the bundle path and the bundle ID as arguments) and Piccolo terminates. The script waits for the old process to be gone, then for `lsappinfo find bundleid=…` to list no instance of the app (see "Restarting has to cope with LaunchServices" under "Desktop acceptance": an `open` while LaunchServices still lists the dead instance fails with -600 and can leave no application frontmost), then runs `open` on the bundle, and runs it again when it fails or no instance shows up within 10 s (20 attempts at most). Failures go to the unified log under the tag `PiccoloRestart`. A helper that cannot be started leaves Piccolo running and shows the reason under the button (`SettingsModel.restartError`).
- One canonical coordinate space inside `PiccoloCore`: global display coordinates with a top-left origin and y pointing down, as used by the Accessibility and CGWindow APIs. Convert from AppKit's bottom-left space only at the `PiccoloSystem` boundary.

## Build, sign, run

- `swift test` runs the package's unit tests.
- `scripts/build.sh [debug|release]` builds `build/Piccolo.app` with xcodebuild. A Debug build also builds `build/PiccoloFixture.app`; a Release build (and so `release.sh`) never builds or ships the fixture.
- `scripts/install.sh [debug|release]` (default `release`) builds, replaces `/Applications/Piccolo.app` and relaunches it. Only a Debug build hosts the control server.
- `scripts/accept.sh [filter]` runs the desktop acceptance tests (see "Desktop acceptance").
- `scripts/release.sh [--skip-notarize]` builds a Developer ID signed release (hardened runtime, secure timestamp, no `get-task-allow`), notarizes it, staples the ticket and writes `build/release/Piccolo-<version>.zip`. It refuses without the signing identity, and without the notary settings unless `--skip-notarize`.
- App icon: `design/icon.png` is the source artwork (1024×1024 PNG, interior fully opaque). To replace it, overwrite that file, run `scripts/make-icon.sh --normalize` (makes the interior opaque, regenerates `App/Assets.xcassets/AppIcon.appiconset`), then `scripts/check-icon-render.sh` after a Release build to check the icon the system draws.
- Signing and notarization settings are never committed. Scripts source `${XDG_CONFIG_HOME:-$HOME/.config}/piccolo/signing.env` when it exists (`PICCOLO_CODESIGN_IDENTITY`, `PICCOLO_TEAM_ID`, `PICCOLO_NOTARY_*`) and fall back to ad-hoc signing otherwise. `PICCOLO_SIGNING_ENV` overrides the file's path.
- The Accessibility grant is tied to the bundle ID and the signing identity. Only builds signed with the configured identity may be installed to `/Applications/Piccolo.app`; `scripts/install.sh` refuses ad-hoc builds. Never reset or edit TCC (`tccutil`, the TCC database).

## Debug control channel

Debug builds of Piccolo host a control server (`io.damao.piccolo.control`, a same-user `CFMessagePort`; no network socket) so that scripts and tests can query the app and trigger actions without keyboard input. This is the basis of automated desktop acceptance.

- Requests are `{"command": String, "params": Object}`, responses `{"ok": Bool, "result": Any?, "error": String?}`. Commands: `status`, `window.focusedFrame`, `window.setFocusedFrame`, `action.run`, `focus.history`, `groups.list`, `history.list`, `displays`, `config.status`, `config.load`, `config.reload`, `hotkey.simulate`, `hotkey.press`, `hotkey.release`, `hotkey.escape`, `preview.state`, `loginItem.status`, `loginItem.set`, and the `settings.*` commands below.
- `action.run` runs an `Action` on the focused window. The params are the action exactly as the config file writes it, for example `{"type": "placeWindow", "frame": {"preset": "leftHalf"}}` or `{"type": "moveToDisplay", "direction": "next"}`. The result is `{"target": {x, y, width, height}, "achieved": {…}}` (what was asked for, and the frame read back, which differs when the window refused the size or was shifted back inside its display) or `{"nothingToDo": true}`. The optional param `animation` (`off`, `fast`, `medium` or `slow`) replaces the config's animation for this call, for every kind of action; without it the config in effect decides, as for a shortcut. The call returns after the windows have glided and been placed. Malformed params, an unknown `animation`, an invalid action (a custom frame off the screen) and window errors answer `ok: false` with a message. The logic is `ActionExecutor` in `PiccoloSystem` (planning in `PiccoloCore/Actions`); the app only registers the command.
- `action.run` with an `arrangeGrid` action arranges the most recently focused windows on the focused window's display (the commands are in `App/DebugArrangeCommands.swift`). The optional param `onlyPid` restricts the candidates to one process; every test passes it, so that it never moves the owner's windows. The result is `{"display": index, "windows": [{"window": number, "target": {…}, "achieved": {…}} or {"window", "target", "error": message}]}`, the window in the top-left cell first, or `{"nothingToDo": true}`. A window that fails does not stop the others. `focus.history` answers `{"windows": [numbers]}`, the windows the focus tracker has seen since the app launched, most recently focused first. The control server does not touch `ActionExecutor.live` until a command needs it, so that it never starts the tracker in the app's place (the acceptance test of the launch-time start relies on it).
- A successful `arrangeGrid` records a group of its windows for its display (`LayoutGroupStore` in `PiccoloSystem`, rules in `PiccoloCore/LinkedResize`): the layout, the windows in cell order, the display's visible frame and the achieved frames. An arrangement in which a window failed records none. One group per display, a window in at most one group, in memory only. `action.run` with a `moveDivider` action moves a divider of the group that holds the focused window, as its shortcut would, with the resize step of the config in effect: the caller hands the config's `ActionSettings` to `ActionExecutor.run(_:onlyPid:settings:)` (the hotkey path reads them from the loaded config when the key is pressed; the command reads them from `ConfigController`), so a test that depends on the step loads a temporary config with `config.load` first. `onlyPid` restricts it as it does `arrangeGrid`: a group with a window of another process is dissolved instead of moved. The group is validated when the key is pressed: the windows on screen are read, and a member that is missing or has an edge more than 2 pt from its recorded frame dissolves the group. Then `DividerMove.plan` gives the new layout, the windows whose cell changed are sent to it with `FrameSetter.apply` (those that shrink first, then those that grow), and `LayoutGroup.recordAchieved` records where they ended up; a window that refused its size moves the divider to where it ended up, and the windows whose cell changed with it are sent there once more. A window that cannot be changed ends the move and dissolves the group. The result is `{"moved": true, "display": index, "windows": [{"window", "target", "achieved"} or {"window", "target", "error"}]}`, every window of the group in cell order (`target` is the last frame it was asked for), or `{"nothingToDo": true, "reason", "message"}` with `reason` one of `noFocusedWindow`, `noGroup`, `dissolved` (with `cause`, `missing` or `moved`, and the `window` that broke the group) and `cannotMove` (the window that would shrink is at 10%, or there is no divider that way). `groups.list` answers `[{display, visibleFrame, layout: {rows: [{height, widths}]}, windows: [{window, frame}]}]`, the groups Piccolo tracks, the windows in cell order with their recorded frames.
- `history.list` (`App/DebugHistoryCommands.swift`) answers `[{window, origin, lastAchieved, preset?, step?}]`, the window records Piccolo holds, ordered by window number, in canonical coordinates; `preset` and `step` are there when the window was last placed by a cycling half. `action.run` accepts `{"type": "restoreWindow"}` and answers `{"target", "achieved"}` or `{"nothingToDo": true}`.
- Column-first grids: `ActionSettings.gridFillOrder` (config key `gridFillOrder`) decides how `arrangeGrid` numbers the cells. With `rows` (the default) the layout is a row layout and the cells are numbered row by row. With `columns` it is a column layout (`TileLayout` with orientation `columns`, built by `TileLayout.grid(windowCount:rows:columns:fillOrder:)`) and the cells are numbered column by column, top to bottom within a column and columns from left to right, so that 3 windows in 2 × 2 are two stacked on the left and one at full height on the right. Window `i` of an arrangement or of a group sits in cell `i`, and the window in the top-left cell is first in the `arrangeGrid` answer either way. A column layout is the transpose of a row layout and is implemented as one: it stores the transposed row layout with the orientation turned around (`TileLayout.transposed`), and `frames(in:)`, `validate()`, `DividerMove.plan` and `LayoutGroup.recordAchieved` all go through that transpose, with the directions transposed for the divider move (`left`↔`up`, `right`↔`down`): `left` and `right` move the vertical divider between the focused column and its neighbour, and every cell of both columns follows, `up` and `down` move a horizontal divider of the focused column, and the aligned ones of other columns with it. `groups.list` writes a column layout as `layout: {columns: [{width, heights: [...]}]}` and a row layout, as above, as `layout: {rows: [{height, widths: [...]}]}`; the windows are listed in cell order in both. `action.run` reads the fill order from the config in effect, like the resize step, so a test that depends on it loads a temporary config with `gridFillOrder` set first (`withLinkedResize(gridFillOrder:)` in the acceptance tests).
- `displays` answers `[{frame, visibleFrame}]`, the displays as the app sees them in canonical coordinates, the primary first. `config.status` answers `{path, bindingCount, registered: [{id, keyCode, modifiers}], issues: [String]}`. `config.load {path}` loads and applies another file instead of the default one, for this run only, and answers the same; nothing is written to the default location. `config.reload` loads the default location again. `hotkey.simulate {id}` presses the shortcut of a registered binding with real keyboard events (posted at the HID tap) and answers `{posted, fired}` once the hotkey has fired, not when its action has finished; an unregistered binding, or `CGPreflightPostEventAccess()` being false, answers `ok: false` (the command never asks for the permission). The key events must come from a `CGEventSource(stateID: .privateState)`: events from the HID system state reach the system but never fire a registered hotkey.
- Holding a shortcut (`App/DebugConfigCommands.swift`, `App/DebugPreviewCommands.swift`). `hotkey.simulate` posts a key-down and a key-up at once, so with the preview on it is a tap: the action runs on release. `hotkey.press {id}` posts only the key-down of a registered binding's shortcut and answers `{posted, fired}` once the hotkey has fired; the key stays down until `hotkey.release {id}`, which posts the key-up and answers `{posted, released}` once the app has seen the hotkey released (an error when it does not within 3 s). `hotkey.escape` posts an Escape press and release with the modifiers of the binding that is held and answers `{posted, fired}` once the temporary Escape hotkey fired; it answers `ok: false` when nothing is held. Same event source (a private state), HID tap and refusals as `hotkey.simulate`. Two optional params exist to measure Carbon: `hotkey.press` takes `autorepeat: N` (N more key-downs flagged as the keyboard's repeat; the answer adds `presses`, how many presses reached the app in all) and `hotkey.release` takes `modifiersFirst: true` (a flags-changed event with no flags before the key-up, which has none either). `preview.state` answers `{visible, frames: [rect], windows?: [number], heldBindingID?, escapeRegistered, planningError?, last?: {bindingID, result: "ran" | "cancelled", previewShown}}`: whether the highlight is on screen and the frames (canonical coordinates) it is drawn at; the window each frame is for, in the order of the frames, for an arrangement and a divider move (the action queue plans without `onlyPid`, so a test that releases an arrangement checks this list first, and sends `hotkey.escape` when a window other than its own is in it); the binding whose shortcut is down; whether the temporary Escape hotkey is registered; why the latest plan showed nothing, when it failed; and what became of the last hold (`previewShown` is true when the highlight really reached the screen during it, false for a tap, and for a press with the preview off, which is a run). A window of Piccolo's process is on screen at each frame, on layer 25; look for it by pid and frame (`PiccoloOverlays` in the tests), `PiccoloWindows.onScreen` only lists layer 0.
- `notice.state` (`App/DebugNoticeCommands.swift`) answers `{visible: Bool, last?: {kind, text, frame}}`: whether a notice is on screen, and the latest one shown since launch, with its stable name (`FailureNotice.rawValue`), the text shown (in the language Piccolo runs in; tests ask `InterfaceTexts.notice(_:)` for the same text, never an English literal) and the panel's frame in canonical coordinates. A window of Piccolo's process is on screen at that frame, on layer 25 (`PiccoloOverlays`). `last` is not cleared when the notice goes, so a test that expects no new notice compares it with its value before. The acceptance tests are `FailureNoticeTests.swift`.
- `settings.*` drive the Settings model the window uses (`App/DebugSettingsCommands.swift`). `settings.open` and `settings.close` answer the state (`settings.open` answers at once, before the system has activated Piccolo, so `isActive` and `isKey` in its answer can still be false: poll `settings.state`); `settings.state` answers `{isOpen, isActive, isKey, bindings: [{id, action, summary, section, visible, active, shortcut?, shortcutText?}], resizeStep, animation, gridFillOrder, destinationPreview, search, issues, tab, loginItem, selectedBindingID?, error?, recordingBindingID?}`, where `isActive` is whether Piccolo is the active application (`NSApp.isActive`) and `isKey` whether the Settings window is the key window of the active app, `animation` and `gridFillOrder` are the names of the config file and `destinationPreview` is a boolean, where `loginItem` is the login item's status (see `loginItem.status`), `action` is written as in the config file, `shortcutText` reads like `⌃⌥⇧⌘F14`, `search` is the text in the search field, `section` is the binding's kind by its config name (`placeWindow`, `moveToDisplay`, `arrangeGrid`, `moveDivider`; the list shows one section per kind in that order, file order inside), `visible` whether the list shows it under the current search and `active` is false only for a shortcut that is not registered (the system refused it, or `ShortcutPlan` could not register it; the app computes `SettingsSnapshot.inactiveBindingIDs` in `ConfigSettingsBackend.current()` as the bindings with a shortcut whose ID is not in `ShortcutManager.Status.registered`, and the model reports none while a recording has the hotkeys suspended), `tab` is `"shortcuts"` or `"general"` and `selectedBindingID` is the binding the list has selected (absent when there is no binding; loading a config selects its first binding unless the selected one is still in it). `settings.select {id}` selects that binding in the list, as a click on its row does, and `settings.showTab {tab}` (`"shortcuts"` or `"general"`) switches the tab; both set the model state the window is bound to, so an open window follows them (they exist so that a review without a person at the mouse can look at each tab and each binding), answer the state, and answer `ok: false` for an ID no binding has or an unknown tab. Neither saves anything; `settings.showTab` also works with the window closed, which then opens on that tab. `settings.setSearch {text}` sets the query as typing it does (the grouping and filter are `BindingSections.make` in `PiccoloUI`: summary or shortcut text contains the trimmed query, ignoring case and diacritics; the selection stays when still shown, else moves to the first shown binding or none) and answers the state; the query is view state and saved nowhere. `settings.addBinding`, `settings.removeBinding {id}`, `settings.updateAction {id, action}` and `settings.setResizeStep {value}` (a fraction: 0.1 is 10%) answer the state, or `ok: false` with the model's message when the edit is rejected (nothing is saved then). `settings.setAnimation {value}` (`off`, `fast`, `medium` or `slow`), `settings.setGridFillOrder {value}` (`rows` or `columns`) and `settings.setDestinationPreview {enabled}` do the same for the three settings, and `ok: false` for a name the format does not know. `settings.restoreDefaults` replaces the bindings with the default shortcuts without the confirmation alert, keeps the settings, and answers the state with `backup`: the name of the copy kept next to the config file, or `null` when there was no file. Edits write the file Piccolo has loaded, so run `config.load` with a temporary file first: they never touch the default location unless that is what is loaded. `settings.beginRecording {id}` suspends every hotkey (`config.status.registered` is empty) until `settings.cancelRecording`, a recorded key, a removal of the binding or `settings.close` (which also ends a recording when the window is closed). `settings.record {id, keyCode, modifiers}` begins recording on that binding and posts one key press with real keyboard events (a private event source at the HID tap, as `hotkey.simulate` does); it answers the state once the recorder has taken the press, with a rejected shortcut in `error` and not as `ok: false`. It refuses (`ok: false`, nothing posted) unless Piccolo is the frontmost application and the Settings window is key, so that the key can never land in another app; bring Piccolo forward through LaunchServices (`open` on the app) first.
- `loginItem.status` answers `{status}` and `loginItem.set {enabled}` answers `{status}` after registering or unregistering Piccolo as a login item (`SMAppService.mainApp`, which stands for the running bundle, so only the app can ask: neither `piccoloctl` nor a test process can). The status is one of `enabled`, `notRegistered`, `requiresApproval` (the user has to allow it in System Settings) and `notFound`; both commands read it from the system, and `settings.state` reports the same as `loginItem`. `loginItem.set` runs the model method behind the switch in the General tab; a refusal answers `ok: false` with the system's message, and asking for the state already in force does nothing. Registering shows a system notification on the machine and changes its Login Items, so only the acceptance test that restores it (see "Desktop acceptance") and a person use it. Measured on macOS 27: an app that was never registered reports `notFound`, and `notRegistered` once it has been registered and unregistered: no API goes back to `notFound`, and neither state is a login item.
- The language, in `settings.state` and two commands. `settings.state` also answers `language` (the stored choice: `"system"` or a code), `effectiveLanguage` (the localization the running app uses: a code, never `"system"`), `restartRequired` and, after a restart that could not be arranged, `restartError`. `settings.setLanguage {language}` (`"system"`, `"en"`, `"zh-Hans"`, `"zh-Hant"`, `"ja"`, `"fr"`, `"es"`, `"pt-BR"` or `"de"`) stores the choice as the picker does and answers the state; anything else answers `ok: false` and lists the values. It changes `AppleLanguages` in Piccolo's defaults domain, which outlives a test run, so only the language tests use it (see "Desktop acceptance"). The running app keeps its language until it restarts. `settings.restartNow` runs the code path of the Restart Now button and answers (the state, with `restarting: true`) before Piccolo quits, 0.3 s later; the new process answers on the control channel again a second or so after that, so a caller waits for a pid other than the old one.
- `window.setFocusedFrame` and every action apply a frame with `FrameSetter.apply`: size, position, size, read back. A window whose size is not settable (fixed-size) still moves to the target's origin. Actions pass the target display's visible frame, and a window that ends up sticking out of it (it refused the size) is shifted left and up until it lies inside, never past the top-left corner. `window.setFocusedFrame` knows no display and does not shift.
- Window animation: every action glides its windows to their new frames over the duration of `ActionSettings.animation` (Off, Fast 0.15 s, Medium 0.25 s, Slow 0.4 s), then places them exactly as without animation. The pure part is in `PiccoloCore/Animation`: `FrameInterpolation` gives the frame at progress t (each edge on the ease-out cubic `1 - (1 - t)^3`, rounded to whole points, exactly the start at 0 and the target at 1) and `AnimationEligibility` decides that a window is not animated when its start and target are within 1 pt on every edge or lie mostly on different displays. `WindowAnimator` (`PiccoloSystem/Animation`) drives all windows of an action on one clock with an injected `AnimationClock`: at most 60 ticks a second, progress taken from the clock (slow Accessibility calls drop frames and never stretch the animation), the last tick at progress 1. A tick sends a window only what changed, the position first when its top or left edge moves towards the corner and the size first otherwise, so that the window stays within its old and new frame. A window whose size is not settable animates its position only; a window whose change throws, or whose tick takes longer than the whole duration, is dropped from the animation and only gets the final apply. A divider move animates the first round of `send` with the windows that shrink first, and a dropped window also stops the windows behind it, so that none grows into space that was not freed; the second round for refused sizes is not animated. After the animation `FrameSetter.apply` places every window in the order of an action without animation, so the achieved frames, the shift into the visible frame and the errors are unchanged. Only an `ActionExecutor` that was given an animator animates (`ActionExecutor.live` has one; the default has none, which keeps the executor's unit tests on the plain path). A shortcut pressed during an animation runs after it, because the action queue is serial.
- `swift run piccoloctl app <command> [--params '<json>']` sends a command (`--service <name>` picks another server, `--timeout <seconds>` raises the 5 s default). `piccoloctl fixture <command>` is the same aimed at the fixture app's server (`io.damao.piccolo.fixture.control`). `piccoloctl windows`, `screens` and `frontmost` read the desktop directly. All output is one line of JSON on stdout; exit code 0 only on success. Frames are in canonical coordinates.
- Release builds contain no control code: the server is under `#if DEBUG`, and `Piccolo.xcodeproj` links `PiccoloControl` into the `Piccolo` app in Debug only (a build-only target dependency plus `OTHER_LDFLAGS` for Debug). Do not add `PiccoloControl` to the app's linked frameworks, and check that `strings` on a Release binary finds no `PiccoloControl`. The `PiccoloFixture` target links it the normal way; it is never part of a release.
- Handlers run on the server's own queue, not on the main thread. Accessibility calls have a 2 s messaging timeout.
- App names are localized: match on `bundleID` (`com.apple.finder`), not on `name`.

## Desktop acceptance

Every feature that moves or resizes real windows ships with acceptance tests that the implementer runs before opening the PR. The tests drive the installed Debug Piccolo and the fixture app, and assert on frames measured in the window server.

- Run it: `scripts/accept.sh [filter]`. It takes the machine-wide lock (waits up to `PICCOLO_ACCEPT_LOCK_TIMEOUT` seconds, default 600, then exits 75 with "locked"), runs `scripts/install.sh debug` (so a signing identity is required and the Accessibility grant is kept), launches the fixture, runs `PICCOLO_ACCEPTANCE=1 swift test --filter PiccoloAcceptanceTests` and prints a one-line `accept: PASS|FAIL` summary. The exit code is the test result; the full test log is `build/accept-test.log`. `filter` is a regular expression matched against the Swift test function names (`scripts/accept.sh setFocusedFrame`). Teardown (close fixture windows, quit the fixture, release the lock) always runs, also on failure, Ctrl-C and SIGTERM. The Debug Piccolo stays installed afterwards. Plain `swift test` skips these tests.
- The fixture is `PiccoloFixture` (`io.damao.piccolo.fixture`, regular app, Debug only, sources in `Fixture/`), built to `build/PiccoloFixture.app`. Its control server `io.damao.piccolo.fixture.control` answers `open {id, frame, minSize?, maxSize?, resizeIncrements?, resizable?}`, `focus {id}`, `miniaturize {id}`, `deminiaturize {id}`, `list` (with `isKey` and `isMiniaturized`), `keyEvents {id}` (`{keyCodes: [Int]}`, the key codes of the key-down events the window received, oldest first; a key that a global hotkey took never gets there), `close {id}`, `closeAll` and `quit`; try them with `piccoloctl fixture <command> --params '<json>'`. Frames are canonical and include the title bar. A command answers only after its window operation has taken effect. Windows have no open or close animation, which would make frames read slightly off for a moment. `NSWindow.resizeIncrements` alone makes AppKit snap Accessibility resizes to the nearest multiple; `minSize` clamps them; `resizable: false` makes `AXSize` refuse.
- Add a test: write another `@Test` in the `Desktop acceptance` suite (`Tests/PiccoloAcceptanceTests/`). A group of tests in its own file is a suite nested in it (`extension DesktopAcceptanceTests { @Suite struct ... }`), which inherits `.serialized` and the `PICCOLO_ACCEPTANCE` switch; acceptance tests must never run at the same time. A test whose numbers depend on the displays derives them from `Layout.screens()` (the displays as the app reports them with `displays`) and skips with `try Test.cancel("reason")` when this machine cannot hold them. Wrap the body in `withFixture`, open windows with `fixture.open`, bring one forward with `Focus.bring`, act through `PiccoloClient`, then assert on `Measure.waitForFrame` (CGWindowList by window number, 1 pt tolerance) and not on the response alone. Never sleep for a fixed time: use `eventually` and make the failure message say what was expected and what was measured. Take test frames from `Layout.screens()` rather than hard-coding coordinates. Identify apps by bundle ID or pid, never by name.
- Tests that register hotkeys (`ConfigHotkeyTests.swift`) write a config into a temporary directory and apply it with `config.load` inside `withConfigDirectory`, which always ends with `config.reload`, checks that Piccolo is back on the default config and that the default config folder is unchanged. They use only control + option + shift + command with F13 to F19 (`TestShortcut`): the hotkeys are live system-wide while a test runs.
- Tests of the destination preview (`DestinationPreviewTests.swift`, the nested suite `Destination preview`) hold shortcuts with `hotkey.press`, `hotkey.release` and `hotkey.escape`, inside `withConfigDirectory` with `TestShortcut`s. The shortcut that is held is always one whose action finds a window of the fixture focused: the release runs it, and no test releases an arrangement before `preview.state.windows` has been checked to list the fixture's windows only (otherwise it sends `hotkey.escape` and fails without releasing). Whatever a test leaves held is cancelled by the `config.reload` that ends `withConfigDirectory`. "carbon 1" and "carbon 2" are the measurements documented on `CarbonHotkeyBackend`. The highlight never makes Piccolo the active application, so these tests need no restart of Piccolo; the checks are that the fixture is still frontmost (`Frontmost.state()`) and its window still the one Piccolo reports as focused while the highlight is up.
- Tests that drive Settings (`SettingsWindowTests.swift`) run inside `withSettingsSession`, which wraps `withConfigDirectory`: it loads a temporary config before anything is edited (Settings writes the file Piccolo has loaded), and afterwards cancels a recording, closes Settings and checks that no window of Piccolo is left on screen. Windows of Piccolo are seen in `CGWindowList` by pid (`PiccoloWindows`), not through Piccolo. `SettingsSession.record` hands Piccolo to LaunchServices until `lsappinfo` reports it frontmost and then retries `settings.record` while it refuses for focus reasons.
- Tests of the login item (`LoginItemTests.swift`) need no window and no config session. The one that always runs only reads: `loginItem.status` answers one of the four states and `settings.state.loginItem` agrees. The one that registers and unregisters runs only with `PICCOLO_LOGIN_ITEM=1` (`PICCOLO_LOGIN_ITEM=1 scripts/accept.sh loginItem`), because registering shows a system notification and changes the machine's Login Items. It remembers the status, enables (expects `enabled` or `requiresApproval`), disables (expects `notRegistered`) and puts the status back in `withLoginItemRestored`, also when it fails. Run it only as often as needed, and never enable the login item by other means.
- Acceptance tests must pass whatever the machine's language is. Piccolo follows it (Simplified Chinese on the owner's Mac), and a test that compares a text it reads from Piccolo neither runs Piccolo in English nor compares with an English literal: it asks `InterfaceTexts` (`Tests/PiccoloAcceptanceTests/InterfaceTexts.swift`) for the same text in the language `settings.state.effectiveLanguage` reports, from the same catalog and the same code (`ActionSummary.text(for:bundle:)`, `SettingsMessages.describe(_:bundle:)`, over `AppLanguage.textBundle`). So Piccolo stays as a person left it, the tests never touch the language choice, and they hold for all eight languages. Do not write the text of an action, a message or a label as a literal in an acceptance test; the translations themselves are checked by the unit tests of `PiccoloUI`. Control channel texts (errors of `settings.select`, `settings.record`, `action.run`) are not translated and may be compared as literals.
- Tests of the language (`LanguageTests.swift`) are the only ones that change the choice, and each runs inside `withLanguageRestored`: it reads `settings.state.language` and `effectiveLanguage` first and afterwards, also when the test failed, stores the choice found at the start and restarts Piccolo (`PiccoloProcess.restart`) if it no longer runs in the language it ran in then, so that the tests after it find the usual Piccolo. A failure to put it back is recorded as a second issue of the test, like `withLoginItemRestored`. They pick the language to switch to from the one Piccolo runs in (`zh-Hans`, or `en` when it already does), so that a restart is needed on any machine. One sets `zh-Hans`, restarts and checks `effectiveLanguage` and a Chinese summary for a `leftHalf` binding, then does the same for `en`. One runs `settings.restartNow` and waits up to 10 s for a new pid that reports the chosen language, then checks that `lsappinfo front` is not `com.apple.loginwindow` and that the restart helper has exited. One checks the state fields and that the running texts keep their language until the restart. After a run, `defaults read io.damao.piccolo AppleLanguages` must say what it said before (on a Mac where Piccolo was never given a language: `Could not find key`). A stress test, off in a normal run, restarts through `settings.restartNow` over and over, half of the rounds with the Settings window frontmost, and checks after each that a new process answers within 10 s and that the desktop can still activate another application: `PICCOLO_STRESS=1 scripts/accept.sh restartNowStress` (`PICCOLO_STRESS_COUNT` sets the number of rounds).
- A Piccolo process that has been the active application stops firing `hotkey.simulate`: the key events are posted and delivered, but the system no longer matches them against the process's hotkeys, whatever is in front afterwards and however the hotkeys are registered again (measured on macOS 27, also with the Debug build of `main`, and no variation of the posting that was tried, tap location or event source, changes it; this has been observed only for the key events `hotkey.simulate` posts). Real key presses are not affected: the owner checked on an installed build that a shortcut still fires after the Settings window has been in front, without a restart. For `hotkey.simulate`, only a new process fires again. A test that brings Piccolo forward therefore ends by restarting it (`PiccoloProcess.restart`; `withSettingsSession` does so for every session that activated it), so that the tests after it find a Piccolo that fires, and a test that wants a hotkey to fire after typing into Settings restarts it first and loads its config again (`SettingsSession.restartPiccolo`).
- Restarting has to cope with LaunchServices. For a moment after a process has died, LaunchServices still lists its instance as running (`lsappinfo find bundleid=io.damao.piccolo` shows it), and an `open` in that moment goes to the dead instance: it fails with error -600 (`_LSOpenURLsWithCompletionHandler() failed`, sometimes -609), and it leaves the window server waiting for that instance to check in. `lsappinfo front` then reports `com.apple.loginwindow` although the screen is not locked, and no other application can be brought to the front any more (every `Focus.bring` after it times out) until some live application is activated; the unified log shows `Setting processToBringForwardAtNextCheckin` for the dead instance's serial number. Measured: of 21 launches that failed this way 17 left the desktop in that state, of 9 that did not fail none did. `PiccoloProcess.restart` therefore does not run `open` while LaunchServices lists an instance of Piccolo (`LaunchServicesRegistry.instances`, polled every 100 ms), and then retries a launch that still fails (a failed `open` is logged, `PiccoloProcess: launch attempt … failed, trying again`, and counted) until the new process answers on its control channel or the timeout runs out. A restart that still fails throws with what was seen. A restart is never wrapped in `try?`: when the test already failed, the restart's own failure is recorded as a second issue of that test (`SettingsSession.restartAfterFailure`). The root suite carries the trait `.piccoloRunning` (`PiccoloRunningTrait.swift`), which makes sure a Piccolo answers before every test and launches the installed one when none does, so that one failed restart fails its own test and not every test after it. Two stress tests, off in a normal run, show all of this: `PICCOLO_STRESS=1 scripts/accept.sh restartStress` restarts Piccolo 30 times (`PICCOLO_STRESS_COUNT` changes the number; every second round after bringing Settings forward, as the Settings tests end), and `restartStressAtOnce` sends SIGTERM and asks for the launch in the same breath, so that LaunchServices lists the old instance every time (without the wait it fails in round 2). Both bring a fixture window to the front after every restart, without the repair `Focus.bring` makes of a desktop with no frontmost application, and print how many launches had to wait for LaunchServices and how many failed.
- Piccolo never acts on its own windows: with Piccolo frontmost, `FocusedWindow.current()` throws `WindowError.ownWindow`. An Accessibility request to the calling process is answered on the calling thread and AppKit stops a window change that is not on the main thread, so an action run by a hotkey pressed while the Settings window had the focus used to crash the app. Code that enumerates windows (grid arrangement) must leave Piccolo's own windows out for the same reason.
- Focus must be verified, never assumed. Since macOS 14 an app cannot always activate itself: a plain `focus` request fails while another app is frontmost. `Focus.bring` therefore hands the fixture to LaunchServices (`open`) first, repeats until it observes the fixture as frontmost (via `lsappinfo`; `NSWorkspace.frontmostApplication` goes stale in a process without an app run loop), the window as key, and Piccolo's own `window.focusedFrame` agreeing, and fails with all three observations otherwise. `loginwindow` as the frontmost application means one of two things, and `Frontmost.state()` tells them apart (`CGSSessionScreenIsLocked` in the session dictionary, read-only): the screen is locked (the failure says so at once; it locks after the idle time set in the screen saver settings, an unattended machine stays locked, no focus-dependent test can pass until the owner unlocks it, and nothing in the repository can fix that), or no application is frontmost while the screen is not locked, which is the state a failed `open` of a dead Piccolo leaves behind (see the previous item). The latter is cleared by activating any live application; when it lasts a second `Focus.bring` hands the front to Finder through LaunchServices (not to Piccolo, which would then stop firing simulated hotkeys) and says so in the log. Its failure message says which of the three cases it saw: locked, no frontmost application, or another application frontmost.
- A frame measured right after a command can still show the previous state, so always poll. Do not post input events from a test or a shell (the one place that posts them is Piccolo itself, in `hotkey.simulate`), take screenshots or script other apps: any of these can raise a permission prompt nobody is there to click.
- `NSScreen.visibleFrame` is only accurate to 1 pt. The Dock and the menu bar can be half a point thick at 2x, the window server enforces the real size, and a command line process can see a different value than the app does. A window that spans the full width or touches the top can therefore come back 1 pt smaller than its target. Never assert exact equality with a display's visible frame: compare with the 1 pt tolerance. Feature code stores the achieved frame, not the target, whenever it needs to recognise a window later.

## Workflow

Developed with the global `orchestrate` skill: the owner files issues and makes product decisions; Claude writes each issue as a spec, Claude subagents implement it as a PR, Claude reviews, merges and releases. Milestones M0–M5 are GitHub milestones. Piccolo's own rules:

- Desktop acceptance (anything that moves real windows or installs the app) is a machine-wide shared resource: one run at a time. Run `scripts/accept.sh`, not its pieces: it holds the lock and always tears down.
- Release gate: `swift test` and `scripts/build.sh release` on the exact commit to be tagged. Re-run `scripts/accept.sh` there only if code (anything outside documentation) changed since the last full acceptance pass on `main` or on the merged PR result. The published asset, downloaded again, has the SHA-256 of the local archive, is stapled, is assessed as `Notarized Developer ID`, and has no control code and no `get-task-allow`.

## Rules for implementers

- Keep logic in `PiccoloCore` and write the tests for the specified behaviour before the implementation.
- Never commit signing identities, key locations or machine-specific paths. Never read or print notarization key files.
- Do not add third-party dependencies or install tools unless the issue says so.
- Comments and docs in English. Conventional Commits.
