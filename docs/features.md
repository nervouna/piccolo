# Feature internals

## Applying frames and animation

- `window.setFocusedFrame` and every action apply a frame with `FrameSetter.apply`: size, position, size, read back. A window whose size is not settable (fixed-size) still moves to the target's origin. Actions pass the target display's visible frame, and a window that ends up sticking out of it (it refused the size) is shifted left and up until it lies inside, never past the top-left corner. `window.setFocusedFrame` knows no display and does not shift.
- Window animation: every action glides its windows to their new frames over the duration of `ActionSettings.animation` (Off, Fast 0.15 s, Medium 0.25 s, Slow 0.4 s), then places them exactly as without animation. The pure part is in `PiccoloCore/Animation`: `FrameInterpolation` gives the frame at progress t (each edge on the ease-out cubic `1 - (1 - t)^3`, rounded to whole points, exactly the start at 0 and the target at 1) and `AnimationEligibility` decides that a window is not animated when its start and target are within 1 pt on every edge or lie mostly on different displays. `WindowAnimator` (`PiccoloSystem/Animation`) drives all windows of an action on one clock with an injected `AnimationClock`: at most 60 ticks a second, progress taken from the clock (slow Accessibility calls drop frames and never stretch the animation), the last tick at progress 1. A tick sends a window only what changed, the position first when its top or left edge moves towards the corner and the size first otherwise, so that the window stays within its old and new frame. A window whose size is not settable animates its position only; a window whose change throws, or whose tick takes longer than the whole duration, is dropped from the animation and only gets the final apply. A divider move and a swap (both through `carryOut`, see below) animate the first round of `send` with the windows that shrink first, and a dropped window also stops the windows behind it, so that none grows into space that was not freed; the second round for refused sizes is not animated. After the animation `FrameSetter.apply` places every window in the order of an action without animation, so the achieved frames, the shift into the visible frame and the errors are unchanged. Only an `ActionExecutor` that was given an animator animates (`ActionExecutor.live` has one; the default has none, which keeps the executor's unit tests on the plain path). A shortcut pressed during an animation runs after it, because the action queue is serial.
- Edge bounce: a Swap Window press that finds no neighbour bounces the focused window towards that side and back instead of failing, when `ActionSettings.animation` is not Off and the executor has an animator. The pure part is `EdgeBounce` (`PiccoloCore/Animation`), a damped spring: at elapsed time s = progress × duration the offset is `A × e^(−s/τ) × sin(2πs/T) / m`, with `A` = 16 pt (`EdgeBounce.amplitude`), `T` = 0.26 s, `τ` = 0.07 s, and `m` the same product at its first peak s* ≈ 0.043 s, so that the first peak is exactly `A`. The constants are private to `EdgeBounce`, and the offset is rounded to whole points. The window goes out 16 pt, comes back past its start by about 2 pt (a negative offset around s ≈ 0.17 s, rounded to −2 pt) and settles: exactly 0 at t = 0 and t = 1, and at rest from 0.26 s on. The duration is 0.42 s (`EdgeBounce.duration`), the same for Fast, Medium and Slow. `left`, `right` and `down` move the whole frame by the offset towards −x, +x and +y and keep the size, so a negative offset is past the start, on the other side of it; `up` squashes instead, the top edge stays and the bottom edge moves up by the offset (on the overshoot the window is 2 pt taller than it was), because macOS keeps windows below the menu bar and would not let a window go further up. `WindowAnimator.bounce(_:from:towards:duration:)` plays it on the animator's clock with the tick schedule of every animation (one private `ticks(for:_:)` serves `animate` and `bounce`: at most 60 ticks a second, progress taken from the clock, the last tick at progress 1), and a tick sends only what changed: the position for `left`, `right` and `down`, the size for `up`. The start frame is the one read when the group was checked; the offset is exactly 0 at progress 1, so the window ends on exactly that frame (a tick sends it only when the window is not there yet), so there is no `FrameSetter` and no shift into the visible frame, and the window may leave its display by up to 16 pt while it is out. The group is not recorded again and not dissolved (the window is back at its recorded frame), the window records are not touched and no window is raised. A slow call drops frames like in any animation but never drops the window. There is no bounce, and `SwapOutcome.Reason.noNeighbour(bounced: false)` says so, when the animation is Off, when the executor has no animator (`ActionExecutor.bounce` in `ActionExecutor+Animation.swift` checks both), when `up` finds the size not settable (the first tick throws `attributeNotSettable` with nothing changed yet), or when an Accessibility call throws during the bounce: the bounce ends there and the window is put back at its start frame with the calls that still work, their errors ignored. Planning never bounces: `planSwap` answers `SwapPlan.noNeighbour` with the window and its frame, `destinations` shows nothing for it, and with a held shortcut the bounce happens when the action runs, on release.

## Linked resize and column-first grids

- A successful `arrangeGrid` records a group of its windows for its display (`LayoutGroupStore` in `PiccoloSystem`, rules in `PiccoloCore/LinkedResize`): the layout, the windows in cell order, the display's visible frame and the achieved frames. An arrangement in which a window failed records none. One group per display, a window in at most one group, in memory only. `action.run` with a `moveDivider` action moves a divider of the group that holds the focused window, as its shortcut would, with the resize step of the config in effect: the caller hands the config's `ActionSettings` to `ActionExecutor.run(_:onlyPid:settings:)` (the hotkey path reads them from the loaded config when the key is pressed; the command reads them from `ConfigController`), so a test that depends on the step loads a temporary config with `config.load` first. `onlyPid` restricts it as it does `arrangeGrid`: a group with a window of another process is dissolved instead of moved. The group is validated when the key is pressed: the windows on screen are read, and a member that is missing or has an edge more than 2 pt from its recorded frame dissolves the group. Then `DividerMove.plan` gives the new layout, the windows whose cell changed are sent to it with `FrameSetter.apply` (those that shrink first, then those that grow), and `LayoutGroup.recordAchieved` records where they ended up; a window that refused its size moves the divider to where it ended up, and the windows whose cell changed with it are sent there once more. A window that cannot be changed ends the move and dissolves the group. The result is `{"moved": true, "display": index, "windows": [{"window", "target", "achieved"} or {"window", "target", "error"}]}`, every window of the group in cell order (`target` is the last frame it was asked for), or `{"nothingToDo": true, "reason", "message"}` with `reason` one of `noFocusedWindow`, `noGroup`, `dissolved` (with `cause`, `missing` or `moved`, and the `window` that broke the group) and `cannotMove` (the window that would shrink is at 10%, or there is no divider that way). `groups.list` answers `[{display, visibleFrame, layout: {rows: [{height, widths}]}, windows: [{window, frame}]}]`, the groups Piccolo tracks, the windows in cell order with their recorded frames. `moveDivider` and `swapWindow` share the group lookup (`lookUpFocusedGroup`, steps 1 and 2: the group of the focused window, checked when the key is pressed) and the sending (`carryOut`: the glide, `FrameSetter.apply`, `recordAchieved` with the second round for refused sizes, dissolving the group on a failing window, `records.recordChange`), both in `LinkedResizeExecution.swift`.
- Swap Window: `Action.swapWindow(Direction)` (config `{"type": "swapWindow", "direction": "left"}`) exchanges the focused window with its neighbour in the group that holds it (`SwapExecution.swift`, `ActionExecutor.swapWindow`; the planning, `planSwap`, is read-only and shared with `destinations`). The neighbour is `SwapNeighbor.neighbor(of:direction:in:)` (`PiccoloCore/LinkedResize`), pure and geometric, so it needs no transpose for a column layout: the layout is laid out in a 10 000 × 10 000 frame without a gap, where neighbouring cells share their edges exactly, and a candidate is a cell whose edge facing the focused cell coincides with the focused cell's edge on the side of the key and whose extent on the other axis overlaps the focused cell's by a positive length; the longest overlap wins, the lowest cell index on a tie, and none gives `noNeighbour`. The two windows trade cells with `LayoutGroup.swappingCells(_:_:)` (windows and their recorded frames exchanged, the layout and the visible frame as they were): each is sent to the other's cell frame (`targetFrames(for: layout, gap:)`, with the gap in effect when the key is pressed), they glide together over `settings.animation` (they pass each other, so they overlap during the glide) and are then placed with `FrameSetter.apply`, the one that shrinks first, and no other window of the group is touched. The group is recorded with the windows exchanged and the same layout, then through `recordAchieved` with that layout as `requested`, so that a window that refused the size of its new cell moves the divider to where it ended up and the windows whose cell changed with it are sent once more, without a glide, exactly as for a divider move. The group stays linked: `moveDivider` works on it afterwards. A window that cannot be changed ends the swap and dissolves the group; each window that was changed is noted with `records.recordChange`. No window is raised or focused: the focused window keeps the focus and moves with its cell, so repeated presses carry it across the group. The outcome is `ActionOutcome.swap(SwapOutcome)`: `.swapped(display:windows:)` (every window of the group in cell order after the swap) or `.nothingToDo(Reason)` with `noFocusedWindow`, `noGroup`, `dissolved(Breakage)` and `noNeighbour(bounced:)` (the answer of `action.run` is in [control-channel.md](control-channel.md)). The destination preview of a swap highlights the two windows' new cells, with the gap, in cell order, and nothing when there is nothing to do. A press with no neighbour answers `noNeighbour(bounced:)`: the focused window bounces with the animation on, and does not with it Off (see "Edge bounce" under "Applying frames and animation"), and the hotkey path shows the notice only when it did not bounce.
- Column-first grids: `ActionSettings.gridFillOrder` (config key `gridFillOrder`) decides how `arrangeGrid` numbers the cells. With `rows` (the default) the layout is a row layout and the cells are numbered row by row. With `columns` it is a column layout (`TileLayout` with orientation `columns`, built by `TileLayout.grid(windowCount:rows:columns:fillOrder:)`) and the cells are numbered column by column, top to bottom within a column and columns from left to right, so that 3 windows in 2 × 2 are two stacked on the left and one at full height on the right. Window `i` of an arrangement or of a group sits in cell `i`, and the window in the top-left cell is first in the `arrangeGrid` answer either way. A column layout is the transpose of a row layout and is implemented as one: it stores the transposed row layout with the orientation turned around (`TileLayout.transposed`), and `frames(in:)`, `validate()`, `DividerMove.plan` and `LayoutGroup.recordAchieved` all go through that transpose, with the directions transposed for the divider move (`left`↔`up`, `right`↔`down`): `left` and `right` move the vertical divider between the focused column and its neighbour, and every cell of both columns follows, `up` and `down` move a horizontal divider of the focused column, and the aligned ones of other columns with it. `groups.list` writes a column layout as `layout: {columns: [{width, heights: [...]}]}` and a row layout, as above, as `layout: {rows: [{height, widths: [...]}]}`; the windows are listed in cell order in both. `action.run` reads the fill order from the config in effect, like the resize step, so a test that depends on it loads a temporary config with `gridFillOrder` set first (`withLinkedResize(gridFillOrder:)` in the acceptance tests).

## Cycling, Restore Window and the window records

- Cycling, Restore Window and the window records. The rules are pure and in `PiccoloCore`: `PresetCycle` (`Actions/PresetCycle.swift`) holds the three steps of the four halves (size along the axis 1/2, 2/3, 1/3 anchored to the preset's edge) and picks the next step from the window's frame, the display's visible frame and the window's record: a window is "at step k" when its frame is within 2 pt (`FrameTolerance`) of the frame of step k, or of the achieved frame recorded for step k of the same preset (a window that refused the exact size still cycles); otherwise the step is 0. `ActionPlanner.plan(_:windowFrame:displays:record:)` uses it for `placeWindow` with a half, and plans `restoreWindow` (`Action.restoreWindow`, written `{"type": "restoreWindow"}`): with a record whose `lastAchieved` the window is still at (2 pt) the target is the record's `origin` on the display that holds most of it, shifted inside the visible frame like any target; when the origin lies on no display it is the same size centred on the window's current display; otherwise `.nothingToDo`. Planning is shared by `run` and `destinations`, so the destination preview shows the next step and the restore target. The records are `WindowRecord` (`origin`, `lastAchieved`, `cycle: CycleStep?` with the preset and step) and `WindowRecords` (`PiccoloCore/History/WindowRecords.swift`, the update rules), kept in memory by `WindowRecordStore` (`PiccoloSystem`, shared by the copies of an `ActionExecutor` like `LayoutGroupStore`) and keyed by `WindowID`; a window without a number (`WindowFrameAccess.windowID` is `nil`) is neither recorded nor restorable and cycles by its frame alone. A run updates the store after it changed a window: a single-window action (`ActionExecutor.run`), every window of an arrangement that was placed (`arrange`) and every window of a divider move or a swap whose cell changed and that was not marked failed (`moveDivider`, `swapWindow`): when the window has no record or is not at its `lastAchieved` (the user moved it since), the frame before the action becomes the new `origin`; `lastAchieved` and the preset step (or none) are then set to what the action achieved. A failed window is not recorded. A restore that ran clears the window's record, and a restore that found nothing to do drops the stale record (a run does; planning never writes). The failure notice `nothingToRestore` is what the hotkey path shows for `restoreWindow` with nothing to do; a cycling press is never a notice.

## Failure notice

- Failure notice: when a shortcut fires and nothing can happen, the user sees why in a short notice in the middle of the display, for about 1 s. `FailureNotice` (`PiccoloCore/Notice`) is the enum of the reasons, its raw value the stable name used on the control channel: `accessibilityNotGranted`, `noWindow`, `ownWindow`, `windowNotChangeable`, `noOtherDisplay`, `nothingToArrange`, `gridDoesNotFit`, `noGroup`, `dissolved`, `cannotMove`, `nothingToRestore`, `noNeighbour`. The mapping is in `PiccoloSystem/FailureNotice+System.swift` (it needs `WindowError` and the outcomes): `FailureNotice(error:)` for a thrown error (`WindowError`, `ArrangePlannerError`; no notice for `ActionExecutionError` and `ActionPlanningError`, which are config errors reported in Settings) and `FailureNotice(outcome:for:)` for an `ActionOutcome` (`moveToDisplay` with nothing to do is `noOtherDisplay`, `arrangeGrid` with nothing to do is `nothingToArrange`, a window that failed inside an arrangement or divider move is `windowNotChangeable`, the divider move reasons map one to one, and so do those of a swap (`noFocusedWindow` is `noWindow`, `noGroup`, `dissolved`, and `noNeighbour`, "No window in that direction", is its own, except that a window that bounced (`noNeighbour(bounced: true)`) gets none); no notice for `placeWindow` with nothing to do or for a success). The texts and symbols are `FailureNoticeText` (`PiccoloUI/Text`, in the `PiccoloUI` catalog like every text of the window) and the panel is `NoticePanel` (`PiccoloUI/Window`): an `NSVisualEffectView` (`.hudWindow`, radius 12 pt) with an SF Symbol and the text in the system font at 15 pt, centred on the visible frame of the display, shown for 1 s and faded out in 0.2 s; a new notice replaces the one showing and restarts the timer. It follows the overlay panel rules ([shortcuts-and-preview.md](shortcuts-and-preview.md#overlay-panels)), at level `.statusBar` (layer 25). `ConfigController.run` (the hotkey path, on the action queue) maps the error or outcome and, when there is a notice, reads the focused window's frame there and shows it on the main thread through `NoticeController` (`App/`), on the display that holds the window, or the one with the mouse when there is none. `action.run` on the control channel and the planning of the destination preview never show a notice; only the run does.

## Onboarding guide

- Onboarding guide: a floating panel that walks a new user through the first minute: grant Accessibility, move a window, arrange two windows. The steps are `OnboardingStep` (`accessibility`, `moveWindow`, `arrange`, `done`), the pure state machine `OnboardingFlow` (`PiccoloUI/Onboarding`, unit tested: the choice of the bindings, which outcomes complete a step, Continue, Skip, the launch rule) and `OnboardingModel` (`@MainActor @Observable`: open or closed, the stored flag, the 1 s auto-advance through an injected scheduler). Step 2 asks for the first `placeWindow` `leftHalf` binding with a shortcut, else the first `placeWindow` binding with one; step 3 for the 2-windows 1 × 2 `arrangeGrid` binding with a shortcut, else the first `arrangeGrid` binding with one; without a binding the step says so and offers Open Settings. A step is completed only while it is showing and the Accessibility grant is there, by a successful hotkey run of its binding (a placed window; an arrangement that placed at least one window): `ConfigController.run` reports each non-failing run (binding ID and `ActionOutcome`) to `OnboardingController.hotkeyRan` on the main thread, next to the notice; `action.run` on the control channel does not count. A done step advances after 1 s. The guide opens at launch when `ConfigController.start()` wrote the default shortcuts (a first launch) and `OnboardingSeen` is not set, from the menu's "Getting Started…" at step 1 whatever is stored, and bringing it forward when it is open leaves it at its step. Finish, Skip Guide and the close button all store `OnboardingSeen` (a boolean in Piccolo's defaults domain `io.damao.piccolo`, through `OnboardingStore`; the app's is `DefaultsOnboardingStore` over `OnboardingDefaults`; tests use `FakeOnboardingStore`). The panel is `OnboardingPanel` (`PiccoloUI/Onboarding`) hosting `OnboardingView`, owned by `OnboardingController` (`App/`): an `NSPanel` with `.titled, .closable, .utilityWindow, .nonactivatingPanel`, level `.floating` (layer 3), `canJoinAllSpaces` and `fullScreenAuxiliary`, 420 pt wide, in the top-right corner (16 pt margin) of the visible frame of the display with the mouse, placed when it is first shown and left where it is while it stays open. It follows the overlay panel rules ([shortcuts-and-preview.md](shortcuts-and-preview.md#overlay-panels)), except that it takes clicks on its buttons (still without activating Piccolo): the shortcuts it asks for act on the focused window of the application the user works in. The close button does what Skip Guide does. Its texts are in the `PiccoloUI` catalog (the menu item in the `App` catalog).

## Settings window

- Settings: the window is an `NSWindow` with toolbar tabs that hosts `ShortcutsTab` and `GeneralTab` (`SettingsWindowController` in `PiccoloUI`, owned by `SettingsController` in `App/`; see "Tabs, sizes and focus" below), not a SwiftUI `Settings` scene: a scene cannot be opened reliably from code in a menu bar app, and the window has to be shown, closed and made key from the menu, from a second launch and from the control channel. "Settings…" (⌘,) in the menu opens it. Launching Piccolo again while it runs (`open /Applications/Piccolo.app`, Finder) calls `applicationShouldHandleReopen` and opens it too. Every way of opening it ends in `SettingsWindowController.show()`, which orders the window front at once and, when Piccolo is not the active application, asks the system to activate it with `NSRunningApplication.current.activate(options:)` and the option `activateIgnoringOtherApps`. That option is deprecated since macOS 14, so it is passed as its raw value `1 << 1`; it is what makes the request work (the measurements, and the fallback should a later macOS stop honouring it, are on `SettingsWindowController.show()`; the acceptance test "Settings in front" catches that). `show()` only orders the window front when Piccolo is active already and never asks LaunchServices to open Piccolo, so a second launch cannot start a loop of reopen events.

- Tabs, sizes and focus (the window's chrome; agreed in #99 item 1). The tabs are the items of an `NSToolbar` in the `.preference` style (the label under the icon, centred, the selected item highlighted): Shortcuts (SF Symbol `keyboard`) and General (`gearshape`), their names `SettingsTabText` (PiccoloUI catalog keys "Shortcuts" and "General"); the window title is the selected tab's name. A toolbar was chosen over an `NSTabViewController` because that one resizes the window by itself from the size of its children, and Piccolo has to own the animation, the anchoring and the limit to the screen. `SettingsModel.tab` is the source of truth both ways: a click on an item sets it, and the controller follows it (`withObservationTracking`), so `settings.showTab` changes the tab of an open window and a window created later opens on it. A tab change also forgets the error of the tab it was made on and reads the login item and the language again when the General tab comes up. The content is `SettingsContentController`: both tabs are hosting controllers with `sizingOptions = []` (a SwiftUI view that sizes its window by itself, as `.preferredContentSize` does through the window's constraints, neither keeps the top edge nor animates) and only the selected one's view is in the window, filling it, without padding.
- Sizes are `SettingsWindowSizing`. Shortcuts: content 640 × 720 pt, resizable down to 560 × 480; the person's resizes and moves while on this tab are saved with `NSWindow.saveFrame(usingName:)` under `PiccoloSettings.shortcuts` (the frame changes the controller makes itself are counted in `ownFrameChanges` and never saved) and restored when the window is created; the General tab's frame is never saved. General: 640 wide and exactly as tall as its content asks (its minimum and maximum content size are that size, and the zoom button is disabled). `GeneralPane` lays `GeneralTab` out at 640 pt in a `ScrollView`, so that the form and the strip of problems with the config file under it each get the height they ask for (in a window as tall as they ask for in sum, a `VStack` gives the strip, whose `ScrollView` is flexible, more than it needs and the form less, which then scrolls), and reports that height with `onGeometryChange` (`GeneralHeight`); the window follows it when it changes: the restart row of the language picker, a login item to approve, a problem with the config file. A change of tab animates the window to the new size (`NSAnimationContext` over `animationResizeTime`; no animation while the window is not on screen or under Reduce Motion; a new size that arrives while an animation is under way replaces it, so the window always ends at the last size asked for: `setFrame(_:animated:)` leaves an animation alone only when it goes to that very frame, because the window's own frame says nothing about an animation that has not moved it yet, and a size to be set without animation is set by an animation that takes no time, since `NSWindow.setFrame` does not stop one under way; each animation counts itself in `ownFrameChanges` and ends its own count, whichever completion arrives first) and keeps its top-left corner: `SettingsWindowSizing.frame(replacing:size:visibleFrame:)` is never taller or wider than the visible frame of the window's screen and moves the window up or left only as far as needed to end inside it, so the top edge stays whenever the new size fits below it. A tab that does not fit on the screen scrolls: the General tab's `ScrollView`, the Shortcuts tab's list. The size is fitted again when the window opens (and once more after it is on screen, because the toolbar takes its height from the frame then) and when it moves to another screen (`windowDidChangeScreen`).
- Focus: opening the window and changing the tab leave no text field with the focus, the window itself being the first responder until the person clicks a field. The system, or SwiftUI, gives the first text field the focus when the window becomes key, which is up to 0.1 s after `show()` when Piccolo was not the active application, and when a tab's view is put in the window. The controller takes it back with `makeFirstResponder(nil)`, at once and on the next turn of the run loop, after a tab change; and for an opening, the first time the window becomes key after `show()` found it not visible or not key (`clearsFocusWhenKey`). A `show()` on a window that is key already (a second launch, a second `settings.open`) takes nothing from a field the person is typing in. The debug control channel reports it as `firstResponder` (see [control-channel.md](control-channel.md)).

- General tab: without a header, Launch at login and Language; then Moving windows (Window animation as a segmented control, the destination switch), Arranging windows (Window gap, Fill order as two picture tiles, Linked resize step), and one card with Accessibility (amber while the permission is missing) and Config file, with the app name and version under it. A refused window gap or linked resize step shows under its field (`SettingsErrorTarget.field`, through `errorTarget`); a `.window` error (a save that failed) shows above the version, and the config problems are the Shortcuts tab's. The version has 20 pt below it, the room the form has above its first card.
- The login item switch ("Launch at login", General tab) goes through a `LoginItemBackend` the same way: the model reads the status when the tab appears, when the window opens or the app is activated and after every change, and shows a refused change under the switch.

- Keymap model: the Shortcuts tab is described as a keymap of nine sections, `KeymapSection` in `PiccoloCore/Keymap`: Halves, Quarters, Thirds, Other, Displays, Arrange Grid, Move Divider, Swap Window and Custom Areas (raw values `halves`, `quarters`, `thirds`, `other`, `displays`, `grids`, `dividers`, `swaps`, `customAreas`, which the control channel uses). `BuiltInActions.all` is the 30 built-in actions in that order (the 15 presets, Restore Window, the six display directions as next, previous, left, right, up, down, then Move Divider and Swap Window left, right, up, down), `KeymapSection(of:)` gives the section of any action and `Action.isBuiltIn` is false only for `arrangeGrid` and `placeWindow(.custom)`. `Keymap.make(bindings:query:bundle:characterForKeyCode:)` (`PiccoloUI/Model`, pure, so that the rows and the filter are unit tested without a view) answers the sections in order, each a `KeymapGroup` of `KeymapRow`s. A row has a `KeymapRowID` (`.builtIn(Action)` or `.layout(UUID)`, named on the control channel by `KeymapRowID.name`), its action, its name (`ActionSummary` text), its bindings and `isEditable` (true for grid and custom area rows). Every built-in action is a row whether a binding has it or not, and holds every binding with that action in file order (a hand-edited config may bind one action twice; the first binding is the row's `primaryBinding` and `shortcut`); a grid or custom area is one row per binding. A binding without a shortcut counts as no shortcut. The search matches the trimmed query, ignoring case and diacritics, against a row's name and the text of its shortcuts; a section without a matching row is left out, except that with an empty query the grids and custom areas are always there, possibly without rows. `SettingsModel.keymap` is the keymap under the current search.

- Recording by row: `SettingsModel.beginRecording(_ row: KeymapRowID)` suspends the hotkeys, clears the error and drops a pending conflict (a recording that is going on moves to the new row; `isRecording` is true while `recordingRow` is set, and there is no recording by binding ID). `record(_:)` then takes a press for the row: Escape alone cancels (and takes away a reason shown under the row), Delete alone clears like `clearShortcut(_:)` (a built-in row's first binding is removed from the config, a layout row's shortcut becomes `nil` and its binding stays) and ends the recording; a shortcut that cannot be global (`Shortcut.isRegistrable`) is rejected with the error on the row and **recording goes on**, with the hotkeys still suspended; a shortcut another binding has changes nothing, ends the recording and becomes `pendingConflict` (`ShortcutConflict`: the row, the shortcut and the other binding's ID); the row's own shortcut ends the recording with no change; anything else is given to the row (a built-in row's first binding gets it, a built-in row without a binding appends a new binding with that action, a layout row sets its shortcut) and ends the recording. `resolveConflict(replace:)` with `true` makes one commit that takes the shortcut from the other binding (removed when its action is built in, shortcut `nil` when it is a grid or a custom area) and gives it to the row; with `false` it drops the conflict. Beginning a recording, any accepted change (also a no-op one), opening the layout sheet and a reload drop a pending conflict; a change that is rejected does not. A recording of a layout row ends when its binding goes (removal, reload, restoring the defaults); restoring the defaults ends any recording.

- Where an error shows: `SettingsModel.errorTarget` is set with `error` and cleared with it, and is `.row(KeymapRowID)` for a rejected shortcut (the row being recorded or cleared, or the one a conflict was for), `.field(.gap)` or `.field(.resizeStep)` for `setGap` and `setResizeStep`, and `.window` for everything else.

- Layout rows: `addLayout(_:)` accepts `arrangeGrid` and `placeWindow(.custom)` only, appends a binding without a shortcut and begins recording on its row; `updateLayout(_:to:)` replaces a layout's action within the same section, keeping the binding, its place and its shortcut; `removeBinding(_:)` removes one. Both are rejected, with the error on the window and nothing saved, when `layoutProblem(_:editing:)` answers a problem. That is the first of: the config's own validation of the action (`Config.validate()` on a config holding just the action, in its order), with the sentence of `SettingsMessages` and `fields` naming the sheet's fields the failing rule is about (`left`, `top`, `width`, `height`, `windows`, `rows`, `columns`; `x + width` names left and width, `y + height` top and height, `count` windows), then the rule that no other binding of the same section has an equal action (no fields; "There is already a grid like this.", "There is already a custom area like this."). A request that is not about a grid or a custom area (a built-in action to `addLayout`, a grid made a custom area, a binding that is no layout) is rejected with an English-only sentence, since no window makes it. `editLayout(_:)` with `.new(.grids)`, `.new(.customAreas)` or `.edit(id)` sets `layoutEditor`, the request for the sheet of a grid or custom area, ends a recording and drops a pending conflict; `dismissLayoutEditor()` withdraws it, and `SettingsWindowController` does so when the window closes. A reload (a config replaced from outside, restoring the defaults) drops an `.edit(id)` request whose binding is no longer in the config, and keeps a `.new` request and an `.edit(id)` whose binding is still there. The Shortcuts tab shows the sheet for the request (see "The sheet for grids and custom areas" below).

- The Shortcuts tab (`ShortcutsTab`, `PiccoloUI/Views`) shows the keymap: no list with a selection, no editor under it, no status strip at the bottom. At the top is a search field (a magnifying glass, the placeholder "Search", a clear button while it holds text, Escape clears it; it is `SettingsModel.search`, set with `setSearch(_:)`) and a "⋯" pull-down, a 30 pt square as tall as the search field, with "Restore Default Shortcuts…" (it asks for the confirmation, `askToRestoreDefaults()`) and "Reveal Config in Finder" (`SettingsHost.revealConfigInFinder`, so the tab gets the host). Under it `ProblemsBanner` lists `model.issues` and an error whose `errorTarget` is `.window`, as selectable text, at most about four lines high and scrolling beyond that; with nothing to say it is not there. Below, a scrolling column of cards, one per `Keymap.make` section with its header (`KeymapSection.title(bundle:)`: Halves, Quarters, Thirds, Other, Displays, Arrange Grid, Move Divider, Swap Window, Custom Areas); "No shortcuts match" shows when a search leaves no section. A row (`KeymapRowView`) is the glyph, the name, for a grid or a custom area the edit button (a pencil, `editLayout(.edit(id))`), a warning sign when the shortcut is not active, and the shortcut button. The glyph (`ActionGlyph`, 30 × 19 pt) is a small screen with the windows of the action: the frame of a preset or a custom area, the cells of a grid in the current fill order (`ActionPreview.rects(for:fillOrder:)`); a display move is an arrow in the same small screen (bar-ended `arrow.right.to.line` and `arrow.left.to.line` for Next and Previous, standing for ⇥ and ⇤); Move Divider is two light halves split along the divider with the arrow of its direction, the arrow on a pill of the screen's colour so that the split line stops behind it; Swap Window is two filled halves with the arrow on the same pill; Restore Window is a dashed frame in the middle with a turning arrow. `ActionGlyphKind` decides which, from the action, and is unit tested. The shortcut button (`ShortcutRecorderButton`, 128 pt) reads the row's shortcut, or "Record Shortcut" with a dashed border and the secondary colour when it has none, or "Type shortcut…" in the accent colour while it records; clicking it starts a recording (`beginRecording(_:)`) and clicking it again cancels; on hover a ✕ inside it takes the shortcut away (`clearShortcut(_:)`). The key press itself is caught by `SettingsWindowController`, as before. A click on anything in the cards that is not a control ends a recording. A built-in row whose binding list has more than one binding (a hand-edited config) shows each extra one as a small tag before the button, with a ✕ that removes that binding (`removeBinding(_:)`); the interface offers no way to add one. Under a row, in its card, `KeymapRowView` shows the error of the model when `errorTarget` is that row (red text), and for `pendingConflict` of that row an amber box with "%@ is already used by %@." (the shortcut and the name of the other row's action), Cancel (`resolveConflict(replace: false)`) and Replace (`replace: true`). The Arrange Grid and Custom Areas cards end with an "Add Grid…" or "Add Custom Area…" row, which calls `editLayout(.new(.grids))` or `editLayout(.new(.customAreas))`.

- The sheet for grids and custom areas (`LayoutEditorSheet`, `Views/LayoutEditorSheet.swift`; agreed in #99 item 6). `ShortcutsTab` has one `.sheet(item:)` on `LayoutEditorSheet.presentation(of:)`, a binding to `model.layoutEditor`: its `Presentation` is `Identifiable` by the request, so a new request is a new sheet with a fresh draft, and closing the sheet (Escape, Cancel, Done, Delete) goes through `dismissLayoutEditor()`. The sheet is presented from the tab and not from `SettingsWindowController`, because the window is an `NSToolbar` window; the tab's view is only in the window while the tab is selected, so a request made while the General tab is selected waits until the Shortcuts tab is. The sheet keeps its draft in `@State` and gives it to the model only with Done. It starts from `LayoutDraft.newArea` (25%, 25%, 50% by 50%), `LayoutDraft.newGrid` (4 windows in 2 × 2) or the action of the binding being edited, and shows a title (`LayoutEditorText.title`: New Grid, Edit Grid, New Custom Area, Edit Custom Area), two columns, the reason Done is disabled and the buttons. Delete (only when editing) calls `removeBinding(_:)`; Done calls `addLayout(_:)` (which starts recording the new row's shortcut, so the row records right after the sheet closes) or `updateLayout(_:to:)`; both then call `dismissLayoutEditor()`, also when the model refuses, so that its error shows on the tab. Escape is Cancel and Return is Done (`.keyboardShortcut(.cancelAction)` and `.defaultAction`; no field has an `onSubmit`, so Return in a field is Done). Done is disabled while `layoutProblem(_:editing:)` answers a problem, which is asked again for every change of the draft: `LayoutEditorMessage` shows its message in red under the columns, on one line of fixed height (a message that wraps makes the window's smallest height the height of the text at the narrowest width, and the sheet opens as tall as that; a message too long for the line is cut and shown whole in the tooltip), and the fields it names (`LayoutProblem.fields`) get a red outline. The line is there, empty, when there is no problem, so that a message coming and going while an area is dragged does not move the picture under the pointer.
- The rules of the draft are `LayoutDraft` (`PiccoloCore/Keymap`), pure and unit tested with exact values. `snap(_:free:)` snaps a fraction (limited to 0...1) to the nearest third when it is within 0.02 of 1/3 or 2/3 (the `Double` values the presets use, so a snapped third equals the preset's), otherwise to the nearest 0.05; with `free` (⌥ held) to the nearest 0.01 and never to a third. Steps are computed as `(value * n).rounded() / n`, which is the nearest `Double` to the decimal, so a snapped value equals the same number typed. `areaAfterDrag(from:to:startingWith:free:)` takes points as fractions of the picture (limited to 0...1) and the area as it was when the drag began: a drag that starts outside it draws a new one from the snapped start to the snapped current point, in any direction, and answers `nil` (the area stays as it was) while its width or height is under 0.05 (compared with 1e-9 of slack, because 0.35 - 0.30 is 0.04999999999999999), with the sides cleaned of subtraction noise when they are a whole number of hundredths; a drag that starts inside it (its edge counts; an area with no size has no inside) moves it by the distance dragged, keeping its size, with left and top snapped and then limited so that the area ends inside the screen. `grid(pickingRow:column:)` is the grid a cell of the picker makes (rows and columns one more than the cell's numbers, windows rows × columns); `windowRange(rows:columns:)` is 1 to rows × columns and `grid(_:windowsBy:)` steps the windows within it.
- A custom area in the sheet: on the left `AreaPicture`, a 352 × 220 pt picture of the screen with faint guides at 25%, 1/3, 50% (a little stronger), 2/3 and 75% both ways and the area in the accent colour (drawn as far as it is on the screen: a value typed that puts it off shows what is on, one with no size shows nothing). A `DragGesture` with a minimum distance of 1 pt, so that a click changes nothing, gives `areaAfterDrag` the point where it began and the one it is at, with the area at the first change kept in `@State` until the drag ends, and the option key read from `NSEvent.modifierFlags` at every change. The pointer is a crosshair over the picture and an open hand over the area (there is no public move cursor): `onContinuousHover` keeps one cursor pushed on the stack (`PushedCursor`) and pops it when the pointer leaves or the picture goes. On the right Left, Top, Width and Height (existing texts) are `AreaPercentField`s: a field changes the area while the text parses (`fraction(fromPercentText:)`: a number in percent with a point or comma and an optional %, to two decimals of a percent, at most a million percent), a text that does not parse leaves the area as it was, and the text is written again from the area when it changes from outside (a drag; a field's own typing is not rewritten) and when the field loses the focus.
- A grid in the sheet: on the left `CellPicker`, 8 × 8 cells of 18 pt with 3 pt gaps, with the size under it as "%lld × %lld" (the catalog key is "Grid size %lld × %lld", because the build derives a Swift symbol from every key and "%lld × %lld" has no letter to make one of): hovering lights the cells from the top-left corner to the one under the pointer and the size is the hovered one, a click (`SpatialTapGesture`) sets the grid with `grid(pickingRow:column:)`, and with no hover the lit cells and the size are those of the grid (a grid larger than 8 lights every cell of that direction). On the right `GridPreview`, a 320 × 200 pt screen with the layout of `TileLayout.grid` in the current fill order (`model.gridFillOrder`) and every window numbered in the order the fill order gives, and `WindowsStepper`: "Windows" (the text of #99, restored in the catalog), the number and the − and + buttons, each disabled at its end of the range.
- Undo and redo (#99 item 8): every change to the config made in the window can be undone with ⌘Z and redone with ⇧⌘Z. `SettingsModel.commit(_:)` is the one place a change is accepted, and it records the config it replaced: a step is a commit that changed the config (a candidate equal to the config in effect is no step, and neither is a rejected one). `undo()` and `redo()` apply the recorded config through the same validate-and-save path, so a backend that refuses leaves the config, the history, a recording and a pending conflict as they were and sets `error` with the target `.window`. `canUndo` and `canRedo` say whether there is a step (they are observable, and `settings.state` answers them); at most `SettingsModel.historyLimit` (100) steps are kept, the oldest forgotten; a new change after an undo drops the steps that could be redone. Restoring the default shortcuts is one step (`restoreDefaultShortcuts()` records the config it replaced; undoing it saves that config through `SettingsBackend.save`, so it makes no second copy of the file) and so is a conflict that was replaced. `reload()`, which a config replaced from outside ends in (Reload Config in the menu, `config.load`), clears both histories; the refresh that a restore makes does not. Launch at login and the language are not part of the config and not in the history. A successful undo or redo ends a recording (the hotkeys come back), drops a pending conflict and withdraws the request for the sheet of a layout that the step removed; with nothing to undo or redo they do nothing at all. Closing the window keeps the history and drops a pending conflict (`windowWillClose(_:)`), so that a conflict does not come back with the window. Piccolo is a menu bar app without an Edit menu, so ⌘Z would reach nothing: `SettingsWindowController` catches it in its local key monitor (`take(_:)`; `SettingsUndoKey` is the pure decision: ⌘Z or ⇧⌘Z with no other modifier, the key being the one that types Z on the current layout, or the Z of a US keyboard on a layout with no Latin letters). While a row records, the recorder takes every press first, so ⌘Z is a shortcut like any other then and is recorded. Otherwise the press is taken, also when there is nothing to undo, unless the first responder is a text field or the field editor of one (`firstResponderKind == .textField`: the press goes on to the field, which keeps its own undo) or a sheet is open on the window (`attachedSheet`, or a request for the layout sheet in `layoutEditor`). The sheet's own Cancel discards what it edited; there is no undo inside it.

## Language setting and restart

- Language setting: Settings → General has a Language picker under Launch at login: System default and the eight languages, each written in its own language (`AppLanguage.nativeName`). `SettingsModel.language` is the choice and `setLanguage(_:)` stores it through a `LanguageBackend` (the app's is `SystemLanguageBackend`; tests use `FakeLanguage`). It is stored as `AppleLanguages` in Piccolo's own defaults domain, `io.damao.piccolo` (`LanguageDefaults`): one code, or no key at all for System default. That is the key macOS reads for an app's language at launch, and the one System Settings → Language & Region → Applications writes, so the two agree; the config file does not hold the language. A change applies at the next launch: `SettingsModel.effectiveLanguage` is the language the running app was started in (`Bundle.main.preferredLocalizations`, read once at launch) and `restartRequired` says whether the choice differs from it, System default counting as the language the system's own list gives (`LanguageBackend.systemLanguage`, read from the global domain: System default on a Mac set to the language the app runs in needs no restart). When a restart is needed, the tab says so under the picker and offers Restart Now (`SettingsModel.restartNow()`). The model reads the stored choice again when the window opens, the tab appears and the app is activated.
- Restart Now quits Piccolo and starts it again from a helper that does not depend on Piccolo staying alive: `AppRestart` starts `/bin/sh` with a short script (the process ID, the bundle path and the bundle ID as arguments) and Piccolo terminates. The script waits for the old process to be gone, then for `lsappinfo find bundleid=…` to list no instance of the app (see "Restarting has to cope with LaunchServices" in [acceptance.md](acceptance.md): an `open` while LaunchServices still lists the dead instance fails with -600 and can leave no application frontmost), then runs `open` on the bundle, and runs it again when it fails or no instance shows up within 10 s (20 attempts at most). Failures go to the unified log under the tag `PiccoloRestart`. A helper that cannot be started leaves Piccolo running and shows the reason under the button (`SettingsModel.restartError`).
