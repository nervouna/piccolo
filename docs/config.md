# Config and shortcuts

- Config and shortcuts: the config is `~/Library/Application Support/Piccolo/config.json`. Besides the bindings it holds `resizeStep` (default `0.05`), `animation` (`off`, `fast`, `medium`, `slow`; default `fast`), `gridFillOrder` (`rows`, `columns`; default `rows`) `destinationPreview` (a boolean; default `true`) and `gap` (the window gap: an integer number of points from 0 to 64; default `0`; a fraction, a string, `null` or a number out of range takes the default with an issue naming `gap`, as an invalid `resizeStep` does). Every save writes all of them. A missing key takes its default without an issue; a key that cannot be read (an unknown name, a wrong JSON type) takes its default with an issue naming it, and counts as a dropped entry, as an invalid `resizeStep` does. `ActionSettings` (`PiccoloCore`) is what an action reads from the config: the resize step, the animation, the fill order and the gap. The hotkey path passes `ActionSettings(config)` of the config in effect when the key is pressed. A missing file means no bindings, with one exception: at launch, `ShortcutManager.loadAtLaunch(from:)` writes `Config.defaultShortcuts` (the 28 bindings of `PiccoloCore/Config/DefaultShortcuts.swift`) to a missing file through `ConfigStore.createIfMissing`, which never writes over an existing file, and then loads it. `config.load`, "Reload Config" and every other load of a missing file load no bindings and write nothing; the first save from Settings creates the folder too. Settings' "Restore Default Shortcuts…" goes through `ShortcutManager.replaceKeepingCopy(with:)`, which takes the bindings: it copies the file (`ConfigStore.backUp()`) and saves `Config.defaultShortcuts.bindings` in its place, keeping the settings in use. At launch, and on "Reload Config" in the menu, `ShortcutManager` (`PiccoloSystem`) loads it, resolves it with `ShortcutPlan` and registers the shortcuts as Carbon hotkeys through `HotkeyRegistrar` (the Carbon calls sit behind `HotkeyBackend`, so the replace and failure logic is unit tested with a fake). `ShortcutManager.save(_:)` writes an edited config to the file it has loaded (the default location, or the file given to `config.load`) and loads it again; `setSuspended(_:)` releases every hotkey and keeps loads and saves from registering any until it is lifted (see "Settings window" in [features.md](features.md#settings-window)). A hotkey runs its action through `ActionExecutor` on a serial queue, never on the main thread; failures are logged. The action runs when the shortcut is pressed, or, with `destinationPreview` on, when it is released (see [shortcuts-and-preview.md](shortcuts-and-preview.md)). Load issues, plan issues and shortcuts the system refused are logged and listed in `config.status`. When the last load dropped something (a skipped binding or a setting replaced by its default), the first save after it copies the file to `config.backup-<yyyyMMdd-HHmmss>.json` next to it before writing, once per load, and the issue list says where the copy is until the next load.
- Window gap: the config key `gap` (points, 0 to 64, default 0) is carried by `ActionSettings.gap`. The rule is `WindowGap.inset(_:gap:in:)` (`PiccoloCore/Geometry/WindowGap.swift`), the only place it is written: frames are computed without a gap first, edges rounded as before, and then every edge on the visible frame's edge (within 1 pt) moves in by `gap` and every other edge by half of it. A shared divider is rounded once, before the inset, and with an odd gap the left or top edge takes the larger half (`gap - gap / 2`) and the right or bottom edge the smaller (`gap / 2`), so facing edges are exactly `gap` apart on whole points. It is applied by `FrameResolver.frame(for:visibleFrame:currentFrame:gap:)` (presets and custom frames; `center` is capped to `WindowGap.inset(_:by:)` of the visible frame), `PresetCycle.frame/currentStep/nextStep/step(... gap:)` (the steps and their recognition), `TileLayout.frames(in:gap:)` (grid cells and group cells, also through `LayoutGroup.targetFrames(for:gap:)` and `ArrangePlanner.plan(gap:)`), `LayoutGroup.recordAchieved(requested:achieved:gap:)` (reads each divider back through the gap) and `DisplayLayout.frame(moving:from:to:gap:)` (the relative frame is measured in each visible frame inset by `gap`). `ActionPlanner.plan(... gap:)` routes `placeWindow` and `moveToDisplay` through them; `restoreWindow` ignores the gap. `ActionExecutor` hands `settings.gap` to the planners, the arrangement, the divider move and `destinations`, so the destination preview shows the gapped frames. A group does not store the gap: a divider move uses the gap in effect when the key is pressed, and the group is validated against its recorded achieved frames as before. Settings → General has a "Window gap" row (`PointField`) over `SettingsModel.setGap`.
