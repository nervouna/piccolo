# Desktop acceptance

Every feature that moves or resizes real windows ships with acceptance tests that the implementer runs before opening the PR. The tests drive the installed Debug Piccolo and the fixture app, and assert on frames measured in the window server.

- Run it: `scripts/accept.sh [filter]`. It takes the machine-wide lock (waits up to `PICCOLO_ACCEPT_LOCK_TIMEOUT` seconds, default 600, then exits 75 with "locked"), runs `scripts/install.sh debug` (so a signing identity is required and the Accessibility grant is kept), launches the fixture, runs `PICCOLO_ACCEPTANCE=1 swift test --filter PiccoloAcceptanceTests` and prints a one-line `accept: PASS|FAIL` summary. The exit code is the test result; the full test log is `build/accept-test.log`. `filter` is a regular expression matched against the test identifiers: a suite's struct name or a test function name (`scripts/accept.sh SettingsWindow`, `scripts/accept.sh setFocusedFrame`). Which filter a change needs is in "Acceptance scope" under "Workflow". Teardown (hand Piccolo back to the config at the default location with `config.reload`, close fixture windows, quit the fixture, release the lock) always runs, also on failure, Ctrl-C and SIGTERM. The Debug Piccolo stays installed afterwards. Plain `swift test` skips these tests.
- The fixture is `PiccoloFixture` (`io.damao.piccolo.fixture`, regular app, Debug only, sources in `Fixture/`), built to `build/PiccoloFixture.app`. Its control server `io.damao.piccolo.fixture.control` answers `open {id, frame, minSize?, maxSize?, resizeIncrements?, resizable?}`, `focus {id}`, `miniaturize {id}`, `deminiaturize {id}`, `list` (with `isKey` and `isMiniaturized`), `keyEvents {id}` (`{keyCodes: [Int]}`, the key codes of the key-down events the window received, oldest first; a key that a global hotkey took never gets there), `close {id}`, `closeAll` and `quit`; try them with `piccoloctl fixture <command> --params '<json>'`. Frames are canonical and include the title bar. A command answers only after its window operation has taken effect. Windows have no open or close animation, which would make frames read slightly off for a moment. `NSWindow.resizeIncrements` alone makes AppKit snap Accessibility resizes to the nearest multiple; `minSize` clamps them; `resizable: false` makes `AXSize` refuse.
- Add a test: write another `@Test` in the `Desktop acceptance` suite (`Tests/PiccoloAcceptanceTests/`). A group of tests in its own file is a suite nested in it (`extension DesktopAcceptanceTests { @Suite struct ... }`), which inherits `.serialized` and the `PICCOLO_ACCEPTANCE` switch; acceptance tests must never run at the same time. A test whose numbers depend on the displays derives them from `Layout.screens()` (the displays as the app reports them with `displays`) and skips with `try Test.cancel("reason")` when this machine cannot hold them. Wrap the body in `withFixture`, open windows with `fixture.open`, bring one forward with `Focus.bring`, act through `PiccoloClient`, then assert on `Measure.waitForFrame` (CGWindowList by window number, 1 pt tolerance) and not on the response alone. Never sleep for a fixed time: use `eventually` and make the failure message say what was expected and what was measured. Take test frames from `Layout.screens()` rather than hard-coding coordinates. Identify apps by bundle ID or pid, never by name.
- Every test starts from the fresh-install config. The config at the default location is the person's own (on the reviewer's Mac it has `gap: 16` and `gridFillOrder: columns`), and `action.run` and the hotkeys read the settings of the config in effect, so a test that ran on it would measure frames off by the gap. The trait `.piccoloRunning` on the root suite (`PiccoloRunningTrait.swift`, so that no suite can forget it) therefore writes `Config.defaultShortcuts` (gap 0, animation `fast`, grid fill order `rows`, resize step 0.05, destination preview on, the 32 default bindings) to a temporary directory (`FreshInstallConfig.swift`) and loads it with `config.load` before every test; afterwards it loads the default location again with `config.reload` and removes the directory. The default location is never written, and a Settings edit made while the temporary file is loaded changes the temporary file. A test that needs other settings or bindings loads its own config with `withConfigDirectory` (`withLinkedResize`, `withSettingsSession` and `withFixtureOnDefaultSettings` wrap it), which ends by loading the fresh-install config again and not by `config.reload` (that goes to the person's config), so what a test does after it still runs on the defaults. A Piccolo that is restarted inside a test (`PiccoloProcess.restart`, Restart Now) comes up on the config at the default location until the next test starts, so a test that restarts it loads the config it needs before it acts or edits. `scripts/accept.sh` reloads the default location in its teardown as well, for a run that is interrupted mid-test; after a run, `piccoloctl app settings.state` answers the person's own `gap` and `gridFillOrder`, and `shasum -a 256` of the file is what it was before.
- Tests that register hotkeys (`ConfigHotkeyTests.swift`) write a config into a temporary directory and apply it with `config.load` inside `withConfigDirectory`, which always ends by loading the fresh-install config again, checks that Piccolo reports its file and that the default config folder is unchanged. They use only control + option + shift + command with F13 to F19 (`TestShortcut`): the hotkeys are live system-wide while a test runs.
- Tests of the destination preview (`DestinationPreviewTests.swift`, the nested suite `Destination preview`) hold shortcuts with `hotkey.press`, `hotkey.release` and `hotkey.escape`, inside `withConfigDirectory` with `TestShortcut`s. The shortcut that is held is always one whose action finds a window of the fixture focused: the release runs it, and no test releases an arrangement before `preview.state.windows` has been checked to list the fixture's windows only (otherwise it sends `hotkey.escape` and fails without releasing). Whatever a test leaves held is cancelled by the load of the fresh-install config that ends `withConfigDirectory`. "carbon 1" and "carbon 2" are the measurements documented on `CarbonHotkeyBackend`. The highlight never makes Piccolo the active application, so these tests need no restart of Piccolo; the checks are that the fixture is still frontmost (`Frontmost.state()`) and its window still the one Piccolo reports as focused while the highlight is up.
- Tests that drive Settings (`SettingsWindowTests.swift`) run inside `withSettingsSession`, which wraps `withConfigDirectory`: it loads a temporary config before anything is edited (Settings writes the file Piccolo has loaded), and afterwards cancels a recording, closes Settings and checks that no window of Piccolo is left on screen. Windows of Piccolo are seen in `CGWindowList` by pid (`PiccoloWindows`), not through Piccolo. `SettingsSession.record` hands Piccolo to LaunchServices until `lsappinfo` reports it frontmost and then retries `settings.record` while it refuses for focus reasons. `SettingsWindowChromeTests.swift` (the suite `SettingsWindowChrome`: the title, the keyboard focus, the size of each tab) reads the window from `settings.state` (`windowFrame`, `windowTitle`, `firstResponder`, `contentFits`), reads it again until the frame has stopped changing (a tab change animates the window), and puts the window on each display with `settings.moveWindow`.
- Tests of the login item (`LoginItemTests.swift`) need no window and no config session. The one that always runs only reads: `loginItem.status` answers one of the four states and `settings.state.loginItem` agrees. The one that registers and unregisters runs only with `PICCOLO_LOGIN_ITEM=1` (`PICCOLO_LOGIN_ITEM=1 scripts/accept.sh loginItem`), because registering shows a system notification and changes the machine's Login Items. It remembers the status, enables (expects `enabled` or `requiresApproval`), disables (expects `notRegistered`) and puts the status back in `withLoginItemRestored`, also when it fails. Run it only as often as needed, and never enable the login item by other means.
- Acceptance tests must pass whatever the machine's language is. Piccolo follows it (Simplified Chinese on the owner's Mac), and a test that compares a text it reads from Piccolo neither runs Piccolo in English nor compares with an English literal: it asks `InterfaceTexts` (`Tests/PiccoloAcceptanceTests/InterfaceTexts.swift`) for the same text in the language `settings.state.effectiveLanguage` reports, from the same catalog and the same code (`ActionSummary.text(for:bundle:)`, `SettingsMessages.describe(_:bundle:)`, over `AppLanguage.textBundle`). So Piccolo stays as a person left it, the tests never touch the language choice, and they hold for all eight languages. Do not write the text of an action, a message or a label as a literal in an acceptance test; the translations themselves are checked by the unit tests of `PiccoloUI`. Control channel texts (errors of `settings.select`, `settings.record`, `action.run`) are not translated and may be compared as literals.
- Tests of the language (`LanguageTests.swift`) are the only ones that change the choice, and each runs inside `withLanguageRestored`: it reads `settings.state.language` and `effectiveLanguage` first and afterwards, also when the test failed, stores the choice found at the start and restarts Piccolo (`PiccoloProcess.restart`) if it no longer runs in the language it ran in then, so that the tests after it find the usual Piccolo. A failure to put it back is recorded as a second issue of the test, like `withLoginItemRestored`. They pick the language to switch to from the one Piccolo runs in (`zh-Hans`, or `en` when it already does), so that a restart is needed on any machine. One sets `zh-Hans`, restarts and checks `effectiveLanguage` and a Chinese summary for a `leftHalf` binding, then does the same for `en`. One runs `settings.restartNow` and waits up to 10 s for a new pid that reports the chosen language, then checks that `lsappinfo front` is not `com.apple.loginwindow` and that the restart helper has exited. One checks the state fields and that the running texts keep their language until the restart. After a run, `defaults read io.damao.piccolo AppleLanguages` must say what it said before (on a Mac where Piccolo was never given a language: `Could not find key`). A stress test, off in a normal run, restarts through `settings.restartNow` over and over, half of the rounds with the Settings window frontmost, and checks after each that a new process answers within 10 s and that the desktop can still activate another application: `PICCOLO_STRESS=1 scripts/accept.sh restartNowStress` (`PICCOLO_STRESS_COUNT` sets the number of rounds).
- A Piccolo process that has been the active application stops firing `hotkey.simulate`: the key events are posted and delivered, but the system no longer matches them against the process's hotkeys, whatever is in front afterwards and however the hotkeys are registered again (measured on macOS 27, also with the Debug build of `main`, and no variation of the posting that was tried, tap location or event source, changes it; this has been observed only for the key events `hotkey.simulate` posts). Real key presses are not affected: the owner checked on an installed build that a shortcut still fires after the Settings window has been in front, without a restart. For `hotkey.simulate`, only a new process fires again. A test that brings Piccolo forward therefore ends by restarting it (`PiccoloProcess.restart`; `withSettingsSession` does so for every session that activated it), so that the tests after it find a Piccolo that fires, and a test that wants a hotkey to fire after typing into Settings restarts it first and loads its config again (`SettingsSession.restartPiccolo`).
- Restarting has to cope with LaunchServices. For a moment after a process has died, LaunchServices still lists its instance as running (`lsappinfo find bundleid=io.damao.piccolo` shows it), and an `open` in that moment goes to the dead instance: it fails with error -600 (`_LSOpenURLsWithCompletionHandler() failed`, sometimes -609), and it leaves the window server waiting for that instance to check in. `lsappinfo front` then reports `com.apple.loginwindow` although the screen is not locked, and no other application can be brought to the front any more (every `Focus.bring` after it times out) until some live application is activated; the unified log shows `Setting processToBringForwardAtNextCheckin` for the dead instance's serial number. Measured: of 21 launches that failed this way 17 left the desktop in that state, of 9 that did not fail none did. `PiccoloProcess.restart` therefore does not run `open` while LaunchServices lists an instance of Piccolo (`LaunchServicesRegistry.instances`, polled every 100 ms), and then retries a launch that still fails (a failed `open` is logged, `PiccoloProcess: launch attempt … failed, trying again`, and counted) until the new process answers on its control channel or the timeout runs out. A restart that still fails throws with what was seen. A restart is never wrapped in `try?`: when the test already failed, the restart's own failure is recorded as a second issue of that test (`SettingsSession.restartAfterFailure`). The root suite carries the trait `.piccoloRunning` (`PiccoloRunningTrait.swift`), which makes sure a Piccolo answers before every test and launches the installed one when none does, so that one failed restart fails its own test and not every test after it. Two stress tests, off in a normal run, show all of this: `PICCOLO_STRESS=1 scripts/accept.sh restartStress` restarts Piccolo 30 times (`PICCOLO_STRESS_COUNT` changes the number; every second round after bringing Settings forward, as the Settings tests end), and `restartStressAtOnce` sends SIGTERM and asks for the launch in the same breath, so that LaunchServices lists the old instance every time (without the wait it fails in round 2). Both bring a fixture window to the front after every restart, without the repair `Focus.bring` makes of a desktop with no frontmost application, and print how many launches had to wait for LaunchServices and how many failed.
- Piccolo never acts on its own windows: with Piccolo frontmost, `FocusedWindow.current()` throws `WindowError.ownWindow`. An Accessibility request to the calling process is answered on the calling thread and AppKit stops a window change that is not on the main thread, so an action run by a hotkey pressed while the Settings window had the focus used to crash the app. Code that enumerates windows (grid arrangement) must leave Piccolo's own windows out for the same reason.
- Focus must be verified, never assumed. Since macOS 14 an app cannot always activate itself: a plain `focus` request fails while another app is frontmost. `Focus.bring` therefore hands the fixture to LaunchServices (`open`) first, repeats until it observes the fixture as frontmost (via `lsappinfo`; `NSWorkspace.frontmostApplication` goes stale in a process without an app run loop), the window as key, and Piccolo's own `window.focusedFrame` agreeing, and fails with all three observations otherwise. `loginwindow` as the frontmost application means one of two things, and `Frontmost.state()` tells them apart (`CGSSessionScreenIsLocked` in the session dictionary, read-only): the screen is locked (the failure says so at once; it locks after the idle time set in the screen saver settings, an unattended machine stays locked, no focus-dependent test can pass until the owner unlocks it, and nothing in the repository can fix that), or no application is frontmost while the screen is not locked, which is the state a failed `open` of a dead Piccolo leaves behind (see the previous item). The latter is cleared by activating any live application; when it lasts a second `Focus.bring` hands the front to Finder through LaunchServices (not to Piccolo, which would then stop firing simulated hotkeys) and says so in the log. Its failure message says which of the three cases it saw: locked, no frontmost application, or another application frontmost.
- A frame measured right after a command can still show the previous state, so always poll. Do not post input events from a test or a shell (the one place that posts them is Piccolo itself, in `hotkey.simulate`), take screenshots or script other apps: any of these can raise a permission prompt nobody is there to click.
- `NSScreen.visibleFrame` is only accurate to 1 pt. The Dock and the menu bar can be half a point thick at 2x, the window server enforces the real size, and a command line process can see a different value than the app does. A window that spans the full width or touches the top can therefore come back 1 pt smaller than its target. Never assert exact equality with a display's visible frame: compare with the 1 pt tolerance. Feature code stores the achieved frame, not the target, whenever it needs to recognise a window later.

## Reviewer UI captures

- Reviewer UI captures: hold the lock (`lockf -k -t 3600 "$HOME/.local/state/piccolo/accept.lock" <script>`), run `scripts/install.sh debug` from the PR's worktree first, drive the window with `piccoloctl app settings.*` / `onboarding.*`, find it in `piccoloctl windows` (`{windowNumber, pid, frame}`, no layer) by Piccolo's pid, Settings being its largest window, and `screencapture -x -o -l <n>`. Before any `settings.*` edit or `settings.restoreDefaults`, `config.load` a temporary file and stop if that fails: otherwise the edit writes the owner's config at the default location; end with `scripts/install.sh debug` again if Settings came to the front (restarts Piccolo).
- A focus assertion that finds another app's window focused (not the fixture's) usually means someone used the Mac during the run: re-run that suite before treating it as a regression.
