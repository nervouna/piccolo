# Debug control channel

Debug builds of Piccolo host a control server (`io.damao.piccolo.control`, a same-user `CFMessagePort`; no network socket) so that scripts and tests can query the app and trigger actions without keyboard input. This is the basis of automated desktop acceptance.

- Requests are `{"command": String, "params": Object}`, responses `{"ok": Bool, "result": Any?, "error": String?}`. Commands: `status`, `window.focusedFrame`, `window.setFocusedFrame`, `action.run`, `focus.history`, `groups.list`, `history.list`, `displays`, `config.status`, `config.load`, `config.reload`, `hotkey.simulate`, `hotkey.press`, `hotkey.release`, `hotkey.escape`, `preview.state`, `loginItem.status`, `loginItem.set`, and the `settings.*` commands below.
- `action.run` runs an `Action` on the focused window. The params are the action exactly as the config file writes it, for example `{"type": "placeWindow", "frame": {"preset": "leftHalf"}}` or `{"type": "moveToDisplay", "direction": "next"}`. The result is `{"target": {x, y, width, height}, "achieved": {…}}` (what was asked for, and the frame read back, which differs when the window refused the size or was shifted back inside its display) or `{"nothingToDo": true}`. The optional param `animation` (`off`, `fast`, `medium` or `slow`) replaces the config's animation for this call, for every kind of action; without it the config in effect decides, as for a shortcut. The call returns after the windows have glided and been placed. Malformed params, an unknown `animation`, an invalid action (a custom frame off the screen) and window errors answer `ok: false` with a message. The logic is `ActionExecutor` in `PiccoloSystem` (planning in `PiccoloCore/Actions`); the app only registers the command.
- `action.run` with an `arrangeGrid` action arranges the most recently focused windows on the focused window's display (the commands are in `App/DebugArrangeCommands.swift`). The optional param `onlyPid` restricts the candidates to one process; every test passes it, so that it never moves the owner's windows. The result is `{"display": index, "windows": [{"window": number, "target": {…}, "achieved": {…}} or {"window", "target", "error": message}]}`, the window in the top-left cell first, or `{"nothingToDo": true}`. A window that fails does not stop the others. `focus.history` answers `{"windows": [numbers]}`, the windows the focus tracker has seen since the app launched, most recently focused first. The control server does not touch `ActionExecutor.live` until a command needs it, so that it never starts the tracker in the app's place (the acceptance test of the launch-time start relies on it).
- `action.run` with a `swapWindow` action (`{"type": "swapWindow", "direction": "left"}`, also `right`, `up`, `down`) exchanges the focused window with its neighbour on that side in its group, as its shortcut would (the commands are in `App/DebugArrangeCommands.swift`); `onlyPid` restricts it as it does `moveDivider` (a group with a window of another process is dissolved, not swapped). The result is `{"swapped": true, "display": index, "windows": [{"window", "target", "achieved"} or {"window", "target", "error"}]}`, every window of the group in cell order after the swap, or `{"nothingToDo": true, "reason", "message"}` with `reason` one of `noFocusedWindow`, `noGroup`, `dissolved` (with `cause`, `missing` or `moved`, and the `window` that broke the group, as for `moveDivider`) and `noNeighbour`, which adds `"bounced": true` when the focused window bounced towards that side and back (the animation is not Off, and the window let it: `up` squashes the window and needs a settable size) and `"bounced": false` when it did not; the bounce is over when the command answers, so it can only be seen by sampling the window from outside. `groups.list` then lists the windows in the exchanged order. Like every `action.run`, it shows no notice; the hotkey path does (`noNeighbour` for a press with no window on that side, unless the window bounced). The acceptance tests are `SwapWindowTests.swift`.
- `history.list` (`App/DebugHistoryCommands.swift`) answers `[{window, origin, lastAchieved, preset?, step?}]`, the window records Piccolo holds, ordered by window number, in canonical coordinates; `preset` and `step` are there when the window was last placed by a cycling half. `action.run` accepts `{"type": "restoreWindow"}` and answers `{"target", "achieved"}` or `{"nothingToDo": true}`.
- `displays` answers `[{frame, visibleFrame}]`, the displays as the app sees them in canonical coordinates, the primary first. `config.status` answers `{path, bindingCount, registered: [{id, keyCode, modifiers}], issues: [String]}`. `config.load {path}` loads and applies another file instead of the default one, for this run only, and answers the same; nothing is written to the default location. `config.reload` loads the default location again. `hotkey.simulate {id}` presses the shortcut of a registered binding with real keyboard events (posted at the HID tap) and answers `{posted, fired}` once the hotkey has fired, not when its action has finished; an unregistered binding, or `CGPreflightPostEventAccess()` being false, answers `ok: false` (the command never asks for the permission). The key events must come from a `CGEventSource(stateID: .privateState)`: events from the HID system state reach the system but never fire a registered hotkey.
- Holding a shortcut (`App/DebugConfigCommands.swift`, `App/DebugPreviewCommands.swift`). `hotkey.simulate` posts a key-down and a key-up at once, so with the preview on it is a tap: the action runs on release. `hotkey.press {id}` posts only the key-down of a registered binding's shortcut and answers `{posted, fired}` once the hotkey has fired; the key stays down until `hotkey.release {id}`, which posts the key-up and answers `{posted, released}` once the app has seen the hotkey released (an error when it does not within 3 s). `hotkey.escape` posts an Escape press and release with the modifiers of the binding that is held and answers `{posted, fired}` once the temporary Escape hotkey fired; it answers `ok: false` when nothing is held. Same event source (a private state), HID tap and refusals as `hotkey.simulate`. Two optional params exist to measure Carbon: `hotkey.press` takes `autorepeat: N` (N more key-downs flagged as the keyboard's repeat; the answer adds `presses`, how many presses reached the app in all) and `hotkey.release` takes `modifiersFirst: true` (a flags-changed event with no flags before the key-up, which has none either). `preview.state` answers `{visible, frames: [rect], windows?: [number], heldBindingID?, escapeRegistered, planningError?, last?: {bindingID, result: "ran" | "cancelled", previewShown}}`: whether the highlight is on screen and the frames (canonical coordinates) it is drawn at; the window each frame is for, in the order of the frames, for an arrangement, a divider move and a swap (the two windows that trade cells, in cell order; the action queue plans without `onlyPid`, so a test that releases an arrangement checks this list first, and sends `hotkey.escape` when a window other than its own is in it); the binding whose shortcut is down; whether the temporary Escape hotkey is registered; why the latest plan showed nothing, when it failed; and what became of the last hold (`previewShown` is true when the highlight really reached the screen during it, false for a tap, and for a press with the preview off, which is a run). A window of Piccolo's process is on screen at each frame, on layer 25; look for it by pid and frame (`PiccoloOverlays` in the tests), `PiccoloWindows.onScreen` only lists layer 0.
- `notice.state` (`App/DebugNoticeCommands.swift`) answers `{visible: Bool, last?: {kind, text, frame}}`: whether a notice is on screen, and the latest one shown since launch, with its stable name (`FailureNotice.rawValue`), the text shown (in the language Piccolo runs in; tests ask `InterfaceTexts.notice(_:)` for the same text, never an English literal) and the panel's frame in canonical coordinates. A window of Piccolo's process is on screen at that frame, on layer 25 (`PiccoloOverlays`). `last` is not cleared when the notice goes, so a test that expects no new notice compares it with its value before. The acceptance tests are `FailureNoticeTests.swift`.
- `onboarding.*` (`App/DebugOnboardingCommands.swift`): `onboarding.open` opens the guide as the menu item does, `onboarding.close` closes it as Skip Guide does (which stores `OnboardingSeen`), `onboarding.continue` and `onboarding.skip` press those buttons (Continue is Finish on the last step; `ok: false` when the button is not enabled), `onboarding.setSeen {seen}` sets the stored flag so that a test can put back what it found (`seen: null`, or no `seen`, removes the key, so that it reads as never written), and `onboarding.state` answers `{visible, step: "accessibility" | "moveWindow" | "arrange" | "done", done: [steps], moveBindingID?, arrangeBindingID?, seen, seenStored, frame?}` (`seenStored`: whether the key is stored at all; `frame`: the panel in canonical coordinates, while it is on screen). The guide's window is a window of Piccolo's process on layer 3 at `frame` (`PiccoloOverlays`). The acceptance test is `OnboardingTests.swift`; it reads `seen` and `seenStored` first and restores them at the end, also on failure (the key is removed again when it was not stored). After a run, `defaults read io.damao.piccolo OnboardingSeen` says what it said before. None of the commands activates Piccolo.
- `settings.*` drive the Settings model the window uses (`App/DebugSettingsCommands.swift`). `settings.open` and `settings.close` answer the state (`settings.open` answers at once, before the system has activated Piccolo, so `isActive` and `isKey` in its answer can still be false: poll `settings.state`); `settings.state` answers `{isOpen, isActive, isKey, bindings: [{id, action, summary, active, shortcut?, shortcutText?}], resizeStep, animation, gridFillOrder, destinationPreview, gap, search, issues, tab, loginItem, error?}` (and the keymap's fields, below), where `isActive` is whether Piccolo is the active application (`NSApp.isActive`) and `isKey` whether the Settings window is the key window of the active app, `animation` and `gridFillOrder` are the names of the config file and `destinationPreview` is a boolean, where `loginItem` is the login item's status (see `loginItem.status`), `action` is written as in the config file, `shortcutText` reads like `⌃⌥⇧⌘F14`, `search` is the text in the search field and `active` is false only for a shortcut that is not registered (the system refused it, or `ShortcutPlan` could not register it; the app computes `SettingsSnapshot.inactiveBindingIDs` in `ConfigSettingsBackend.current()` as the bindings with a shortcut whose ID is not in `ShortcutManager.Status.registered`, and the model reports none while a recording has the hotkeys suspended) and `tab` is `"shortcuts"` or `"general"`. `settings.showTab {tab}` (`"shortcuts"` or `"general"`) switches the tab; it sets the model state the window is bound to, so an open window follows it (it exists so that a review without a person at the mouse can look at each tab), answers the state, and answers `ok: false` for an unknown tab. It saves nothing, and also works with the window closed, which then opens on that tab. `settings.setSearch {text}` sets the query as typing it does (the filter is `Keymap.make` in `PiccoloUI`: a row's name or the text of one of its shortcuts contains the trimmed query, ignoring case and diacritics) and answers the state; the query is view state and saved nowhere. `settings.removeBinding {id}`, `settings.updateAction {id, action}` and `settings.setResizeStep {value}` (a fraction: 0.1 is 10%) answer the state, or `ok: false` with the model's message when the edit is rejected (nothing is saved then). `settings.setAnimation {value}` (`off`, `fast`, `medium` or `slow`), `settings.setGridFillOrder {value}` (`rows` or `columns`) and `settings.setDestinationPreview {enabled}` do the same for the three settings, and `ok: false` for a name the format does not know. `settings.setGap {value}` (whole points) sets the window gap as the General tab's field does and answers the state, or `ok: false` with the model's message for a value outside 0 to 64 (nothing is saved then); `settings.state` answers it as `gap`. `settings.restoreDefaults` replaces the bindings with the default shortcuts without the confirmation alert, keeps the settings, and answers the state with `backup`: the name of the copy kept next to the config file, or `null` when there was no file. Edits write the file Piccolo has loaded, so run `config.load` with a temporary file first: they never touch the default location unless that is what is loaded. Recording and the rest of the keymap are below.
- The keymap, in `settings.state` and the commands of recording and of the layout rows (the model is in [features.md](features.md#settings-window)). A row is named `placeWindow.<preset>` (`placeWindow.leftHalf`), `restoreWindow`, `moveToDisplay.<direction>` (`next`, `previous`, `left`, `right`, `up`, `down`), `moveDivider.<direction>` or `swapWindow.<direction>` (`left`, `right`, `up`, `down`) for the 30 built-in actions, and by the binding's UUID for a grid or a custom area (`KeymapRowID.name`). `settings.state` also answers `rows: [{row, section, name, editable, shortcuts: [{bindingID, shortcutText, active}], recording}]` (the rows under the current `search`, in the order of the tab, built-in rows always present: `section` is `halves`, `quarters`, `thirds`, `other`, `displays`, `grids`, `dividers`, `swaps` or `customAreas`, `name` is the action's summary, `editable` is true for a grid or a custom area, `shortcuts` are the row's bindings that have a shortcut in file order, `recording` whether the row waits for a key), `recordingRow` (the row's name, absent when no row records), `conflict` (`{row, shortcutText, ownerBindingID, ownerName}`, present from a recorded shortcut another binding has until it is resolved or dropped; `ownerName` is the action's summary, such as Left Half), `errorTarget` (where `error` shows: `{"row": name}`, `{"field": "gap"}`, `{"field": "resizeStep"}` or `"window"`; present exactly when `error` is) and `layoutEditor` (the sheet that was asked for: `{"new": "grids"}`, `{"new": "customAreas"}` or `{"edit": id}`; absent when none). The commands answer the state, or `ok: false` with the model's message when it rejects the request (nothing is saved then): `settings.beginRecording {row}` starts recording on the row, as a click on its shortcut button does, and suspends every hotkey (`config.status.registered` is empty) until `settings.cancelRecording`, a recorded key, the removal of the row's binding or `settings.close` (which also ends a recording when the window is closed); `settings.record {row, keyCode, modifiers}` begins recording on the row and posts one key press with real keyboard events (a private event source at the HID tap, as `hotkey.simulate` does), and answers the state once the recorder has taken the press, so a shortcut that cannot be global (`error`, `errorTarget` the row, `recordingRow` still set), a conflict (`conflict`, `recordingRow` gone, nothing changed) and a shortcut the model rejects come back in the state and not as `ok: false`; it refuses (`ok: false`, nothing posted) unless Piccolo is the frontmost application and the Settings window is key, so that the key can never land in another app (bring Piccolo forward through LaunchServices, `open` on the app, first); `settings.clearShortcut {row}` takes away the row's shortcut (a built-in row's first binding is removed, a layout row keeps its binding); `settings.resolveConflict {replace}` replaces the conflict's shortcut (`true`, in one save) or drops it (`false`), and is `ok: false` when none is pending; `settings.addLayout {action}` adds a grid or a custom area (`action` as the config file writes it) and answers the state with `recordingRow` set to the new row's UUID, or `ok: false` with the message when the action is neither, is invalid, or equals another row of its section (nothing is saved); `settings.updateLayout {id, action}` replaces the action of the grid or custom area with that binding ID within its section, with the same refusals; `settings.editLayout {row}` (a grid or custom area's UUID) or `{new: "grids" | "customAreas"}` sets `layoutEditor` (it ends a recording and drops a conflict); `settings.dismissLayoutEditor` clears it. A row name no row can have is `invalidParams`; a name that is well formed but has no row (a UUID no binding has) is `ok: false` with the model's message. The commands of the binding-ID editor are gone: `settings.select`, `settings.addBinding`, and the binding-ID forms of `settings.beginRecording` and `settings.record` (which take a `row` now; they were `settings.beginRecordingRow` and `settings.recordRow` before the Shortcuts tab became a keymap); `settings.state` no longer answers `selectedBindingID` or `recordingBindingID`, nor the `section` and `visible` of a binding, which the rows carry.
- The history, in `settings.state` and two commands (the model is in [features.md](features.md#settings-window)). `settings.state` also answers `canUndo` and `canRedo`: whether `settings.undo` and `settings.redo` have a step, which every change made through the model is (`settings.setGap`, `settings.record`, `settings.resolveConflict {replace: true}`, `settings.restoreDefaults`, the layout commands, ...; not `settings.setLanguage` or `loginItem.set`, which are not part of the config). `settings.undo` takes back the last change and `settings.redo` applies the last one that was taken back, as ⌘Z and ⇧⌘Z do in the window, through the same validate-and-save path: the config file is written and the hotkeys are registered again. Both answer the state, end a recording (the hotkeys come back) and drop a pending conflict; they answer `ok: false` with "there is nothing to undo" or "there is nothing to redo" and change nothing when `canUndo` or `canRedo` is false, and with the model's message (`error` in the state, `errorTarget` `"window"`) when the config cannot be saved, in which case nothing changed, a recording included. `config.load` and `config.reload` clear the history, as they do for the window; `settings.close` does not. The acceptance tests are `SettingsUndoTests.swift`.
- `loginItem.status` answers `{status}` and `loginItem.set {enabled}` answers `{status}` after registering or unregistering Piccolo as a login item (`SMAppService.mainApp`, which stands for the running bundle, so only the app can ask: neither `piccoloctl` nor a test process can). The status is one of `enabled`, `notRegistered`, `requiresApproval` (the user has to allow it in System Settings) and `notFound`; both commands read it from the system, and `settings.state` reports the same as `loginItem`. `loginItem.set` runs the model method behind the switch in the General tab; a refusal answers `ok: false` with the system's message, and asking for the state already in force does nothing. Registering shows a system notification on the machine and changes its Login Items, so only the acceptance test that restores it (see [acceptance.md](acceptance.md)) and a person use it. Measured on macOS 27: an app that was never registered reports `notFound`, and `notRegistered` once it has been registered and unregistered: no API goes back to `notFound`, and neither state is a login item.
- The language, in `settings.state` and two commands. `settings.state` also answers `language` (the stored choice: `"system"` or a code), `effectiveLanguage` (the localization the running app uses: a code, never `"system"`), `restartRequired` and, after a restart that could not be arranged, `restartError`. `settings.setLanguage {language}` (`"system"`, `"en"`, `"zh-Hans"`, `"zh-Hant"`, `"ja"`, `"fr"`, `"es"`, `"pt-BR"` or `"de"`) stores the choice as the picker does and answers the state; anything else answers `ok: false` and lists the values. It changes `AppleLanguages` in Piccolo's defaults domain, which outlives a test run, so only the language tests use it (see [acceptance.md](acceptance.md)). The running app keeps its language until it restarts. `settings.restartNow` runs the code path of the Restart Now button and answers (the state, with `restarting: true`) before Piccolo quits, 0.3 s later; the new process answers on the control channel again a second or so after that, so a caller waits for a pid other than the old one.
- The window itself, in `settings.state` and one command (`App/DebugSettingsWindowState.swift`). `settings.state` also answers `windowFrame` (`{x, y, width, height}` of the window in canonical coordinates, the origin at the top left of the primary display and y down; absent while the window is not open), `windowTitle` (the title, which is the selected tab's name in the language the app runs in; absent until the window has been created), `firstResponder` (what has the keyboard focus: `"none"` when the window itself or nothing is the first responder, `"textField"` for a text field or the field editor that edits one, `"other"` for anything else; `"none"` while the window is not open) and `contentFits` (whether the selected tab's content fits its visible area without scrolling: no scroll view in the tab has more to show than it shows and, on the General tab, the window is as tall as the tab asks for; absent while the window is not open). `windowFrame` changes while the window animates to the size of a tab, so a caller that wants the end state reads it again until two reads agree. `settings.moveWindow {display}` moves the open window to the top-left corner of the visible frame of a display (an index in the `displays` answer, the primary display first; inset by 40 pt) and fits its size to that display, which is how a test looks at the window on each display; it answers `firstResponder`, `windowFrame`, `windowTitle` and `contentFits` as above, and `ok: false` when the window is not open or there is no such display. The move is not one the person made: it saves nothing, so the frame the Shortcuts tab was left at is not touched.
- `swift run piccoloctl app <command> [--params '<json>']` sends a command (`--service <name>` picks another server, `--timeout <seconds>` raises the 5 s default). `piccoloctl fixture <command>` is the same aimed at the fixture app's server (`io.damao.piccolo.fixture.control`). `piccoloctl windows`, `screens` and `frontmost` read the desktop directly. All output is one line of JSON on stdout; exit code 0 only on success. Frames are in canonical coordinates.
- Release builds contain no control code: the server is under `#if DEBUG`, and `Piccolo.xcodeproj` links `PiccoloControl` into the `Piccolo` app in Debug only (a build-only target dependency plus `OTHER_LDFLAGS` for Debug). Do not add `PiccoloControl` to the app's linked frameworks, and check that `strings` on a Release binary finds no `PiccoloControl`. The `PiccoloFixture` target links it the normal way; it is never part of a release.
- Handlers run on the server's own queue, not on the main thread. Accessibility calls have a 2 s messaging timeout.
- App names are localized: match on `bundleID` (`com.apple.finder`), not on `name`.
